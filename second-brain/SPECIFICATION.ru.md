# «Второй мозг» — спецификация

[Русский](SPECIFICATION.ru.md) · [English](SPECIFICATION.en.md) · [Español](SPECIFICATION.es.md) · [Українська](SPECIFICATION.uk.md)

Версия программы: **2.7.1**

«Второй мозг» — программа для Obsidian, которая раскладывает заметки и сырые мысли по проектам и пишет по ним документы с помощью языковой модели. Пользователь кладёт текстовые файлы во входную папку хранилища. Программа определяет, к какому проекту относится каждая мысль, разбирает её на смысловые единицы, находит дубли, противоречия и устаревшее, собирает по каждому проекту «базу синтеза» и по ней пишет документы: обязательный «Сводный файл» и другие — те, что нужны именно этому материалу.

Этот документ описывает, как программа устроена и как она работает внутри: что решает модель, что — код, что — человек, и почему так. Он для тех, кто хочет разобраться в программе, проверить её поведение или доработать её. Как пользоваться программой шаг за шагом, рассказывает инструкция `ИНСТРУКЦИЯ.md` в папке программы.

Соглашения:

- Имена папок, файлов, полей YAML, команд и значений набраны `моноширинным шрифтом` — в точности как в программе.
- Пороги приведены со значениями по умолчанию. Все они меняются в настройках (раздел 17), большинство — ещё и отдельно для контейнера.
- «Модель» без уточнения — языковая модель (LLM). Модель эмбеддингов всегда называется полностью.
- «Раздел 6.4» — ссылка на раздел этого документа.
- Все примеры проектов и записей выдуманы.

## 1. Назначение и принципы

### 1.1 Назначение

Личная база знаний для человека, у которого много переплетающихся проектов и идей. Записывать можно что угодно и когда угодно: короткую мысль, выгрузку переписки с ИИ, дневник за несколько лет. Ничего не теряется, и структуру не нужно держать в голове: раскладку по проектам, связывание и сведение в связный текст берёт на себя программа.

Программа открытая и не привязана к одной модели. Языковую модель выбирает пользователь: облачную по API, свою на этом компьютере или вручную через веб-чат (раздел 13). Задача двойная: взять на себя сложную логическую работу с проектами и снизить порог входа для тех, кто не знаком с Obsidian. При этом программа не превращается в «чёрный ящик»: пользователь понимает базовые принципы её работы и всегда может посмотреть, что и почему сделано.

### 1.2 Принципы

1. **Одна точка входа.** Информация попадает в систему только через папку `_staging` (раздел 4). Обходного пути нет ни для одного источника, поэтому любой вход обрабатывается одинаково и оставляет одинаковый след.
2. **Ничего не удаляется.** Устаревшее, отклонённое и дублирующее помечается и остаётся доступным (раздел 11.1). Исходные файлы хранятся без изменений.
3. **Модель оценивает, код решает, человек подтверждает.** Модель возвращает оценки: уверенность, ценность, зашумлённость. Решение принимает код, сравнивая оценку с порогом. Всё, что ниже порога, и всё спорное становится вопросом пользователю (раздел 7). Там, где ошибка стоила бы потери смысла, модель сама ничего не решает.
4. **Текст мыслей пишет только человек.** Модель не переписывает записи и не сочиняет мысли за автора. Обработанная запись не правится: изменить мысль — значит добавить новую запись (раздел 4.3). Сжатая моделью версия хранится отдельно от исходного текста.
5. **Сырьё и продукт — разные вещи.** Из записей извлекаются аспекты — атомарные смысловые единицы (раздел 5). Из отобранных аспектов собирается база синтеза, а по ней модель пишет документы (раздел 8) — самостоятельный связный текст, а не пересказ аспектов по одному. Так источники курсовой работы и сама курсовая — разные вещи.
6. **Всё хранится обычными файлами.** Записи, карточки проектов и документы — Markdown с YAML-шапкой в хранилище Obsidian, рабочие данные — JSON в скрытой папке `.system`. Сервер базы данных не нужен: хранилище копируется и синхронизируется как обычная папка.
7. **Запуск только по команде.** Фазы запускает пользователь — без расписания и без фоновой обработки. Прерывание безопасно: после каждого шага состояние сохраняется, и повторный запуск продолжает с того же места (раздел 11.3).
8. **Качество важнее экономии токенов.** Промпты не урезаются ради длины. Если материал не помещается в окно модели, код делит его на части. Расходы ограничиваются деньгами: месячным бюджетом и оценкой перед большим запуском (раздел 14).
9. **Приватность по умолчанию.** Эмбеддинги по умолчанию считаются на этом компьютере (раздел 12). Ключи API лежат рядом с программой, а не в хранилище, и не попадают в синхронизацию.
10. **Каждое предположение проверяется.** Там, где система предполагает, а человек решает, пара «предположение — решение» записывается в лог рефлексии (раздел 15.3). По этой статистике настраиваются пороги (раздел 10.5).

### 1.3 Из чего состоит

- **Программа** — пакет Python `brain` в папке программы. Она выполняет все операции над хранилищем, обращается к моделям, задаёт вопросы и применяет ответы. Запускается командами `python -m brain <команда>` (раздел 20). Пользователю обычно не нужна напрямую: её вызывает плагин.
- **Плагин Obsidian «Второй мозг»** (папка `.obsidian/plugins/vtoroy-mozg/`) — панель, окно настроек, команды и окна вроде «Новая мысль». Сам плагин данные не меняет: он читает снимок состояния `.system/ui.json` и запускает команды программы (раздел 18).
- **Хранилище Obsidian** — все данные пользователя и рабочие данные программы (раздел 3).
- **Модели.** Языковая модель нужна там, где требуется понимание текста (раздел 13). Модель эмбеддингов нужна для поиска похожего (раздел 12). По умолчанию это своя модель на этом компьютере: KaLM-Embedding-Gemma3 12B на llama.cpp.
- **Промпты** — тексты заданий для модели, по файлу на шаг, в папке `prompts/` программы (раздел 9).
- **Настройки** — файл `settings.yaml` рядом с программой (раздел 17).

Общий ход работы:

```
_staging/  — новые файлы
  │
  ▼  Фаза 1 — разбор (python -m brain run)
  ответы на вопросы → ручные правки → приём файлов (копия в _исходники)
  → [массовая загрузка: черновик структуры → его утверждает пользователь]
  → каждая запись: классификация → пороги → уточняющие вопросы → уплотнение
                   → векторы → извлечение аспектов в пул контейнера
  → каждый изменённый контейнер: анализ пула → ценность → сборка базы синтеза
                   → сравнение с прежней версией базы
  │
  ▼  Фаза 2 — документы (python -m brain synth "Контейнер")
  база синтеза → синтез документов → сравнение с прежними версиями → версия в .system/versions

Вопросы с любого шага → open-questions.md и панель плагина →
ответ применяется сразу (из панели) или в начале следующей Фазы 1 (из файла)
```

## 2. Термины

Словарь понятий документа. Если формулировка в тексте расходится с определением здесь, верно определение.

| Термин | Значение |
| --- | --- |
| **Хранилище** | Папка Obsidian (vault), с которой работает программа. Все данные — в ней (раздел 3). |
| **Контейнер** (узел) | Узел графа проектов любого уровня: проект, под-проект, росток идеи или вопрос. Физически — папка с карточкой контейнера, записями, документами и витринами (раздел 3.4). |
| **Карточка контейнера** | Файл `Название/Название.md`: свойства контейнера в YAML-шапке и текст пользователя. |
| **Запись** | Единица информации, которую программа разбирает: мысль, фрагмент дневника, диалог с ИИ, ресурс, ручная правка документа и т. п. Файл `.md` с YAML-шапкой в `_записи/`, `_shared/`, `_unsorted/` или `_на_проверку/`. В коде и полях YAML — `entity`. |
| **Исходник** | Входной файл в том виде, в каком его положили в `_staging`. Хранится без изменений в `_исходники/`; записи ссылаются на него. |
| **Сегмент** | Часть входного файла, ставшая отдельной записью при массовой загрузке (раздел 6.4). Границы — номера абзацев; текст сегмента код копирует дословно, модель его не переписывает. |
| **Служебная шапка** | Необязательные первые строки входного файла: дата `дд.мм.гггг` и подсказка `hint: …` (раздел 4.2). |
| **Подсказка** (`hint`) | Указание пользователя, куда отнести запись. Не диктует результат, а сдвигает уверенность в пользу указанного варианта (раздел 4.4). |
| **Источник** (`source`) | Откуда пришла запись: архив, заметка, чат с ИИ и т. п. Определяется по подпапке `_staging`. Служит навигации и сдвигает порог уплотнения; на веса и ранжирование не влияет (раздел 4.2). |
| **Аспект** | Атомарная смысловая единица, извлечённая моделью из записи: факт, идея, план и т. д. (раздел 5). Хранится не в записи, а в пуле аспектов контейнера, со ссылкой на запись-источник. Основная единица вычислений: на аспектах строятся ценность, дубли, противоречия и ранжирование. |
| **Простой тип аспекта** | Один из восьми фиксированных типов: `fact`, `observation`, `hypothesis`, `idea`, `conclusion`, `question`, `plan`, `judgment` (раздел 5.1). |
| **Составной аспект** | Связка нескольких простых аспектов одного контейнера (не обязательно из одной записи), которая образует одно целое: опыт, обоснованное решение, развилка. Собирается по формуле состава своего типа (раздел 5.2). |
| **Пул аспектов** | Все простые и составные аспекты контейнера с их статусами, оценками ценности, связями дублей и противоречий. Файл `.system/data/pools/<id>.json` (раздел 16.3). |
| **Содержательная ценность** | Оценка аспекта 0–100 в контексте всего контейнера (промпт «Ценность»). Первая ось ранжирования: по ней элементы отсеиваются и делятся на первостепенные и второстепенные (раздел 6.10). |
| **Таблица приоритета** | Порядок групп аспектов по типам в базе синтеза. Вторая, независимая ось ранжирования (раздел 5.4). |
| **Анализ пула** | Один вызов модели по всему пулу контейнера: находит составные аспекты, дубли, устаревшее, противоречия и предложения по структуре (раздел 6.10). |
| **База синтеза** | Итог Фазы 1 для контейнера: отобранные по ценности аспекты, сгруппированные по типам и упорядоченные, с пометками противоречий и развилок. Сырьё для документов (раздел 6.10). |
| **Документ** (продукт) | Текст, который Фаза 2 пишет по базе синтеза: обязательный «Сводный файл» и дополнительные документы, состав которых определяет модель (раздел 8). |
| **Сводный файл** | Обязательный документ контейнера: общее описание проекта. |
| **Витрина** | Файлы `_аспекты.md` и `_база синтеза.md` в папке контейнера: пул и база синтеза в читаемом виде. Только для чтения — программа переписывает их сама. |
| **Фаза 1** | Разбор: приём новых файлов, раскладка записей по контейнерам, извлечение аспектов, сборка баз синтеза (раздел 6). Команда `run`. |
| **Фаза 2** | Написание документов для выбранного контейнера по его базе синтеза (раздел 8). Команда `synth`. |
| **Bootstrap** | Режим массовой загрузки: структуры контейнеров ещё нет или она неполна. Сначала черновик структуры по всему материалу, затем раскладка с делением длинных текстов на сегменты (раздел 6.2–6.3). |
| **Steady-state** | Обычный режим: одна новая запись раскладывается по уже существующей структуре, без деления. |
| **Черновик структуры** | Предложенное моделью дерево контейнеров, которое пользователь правит и утверждает одним файлом `_структура (черновик).md` (раздел 6.3). |
| **Карантин** | Папка `_на_проверку/`: записи, которые программа не смогла уверенно разложить. Ждут ответа на вопрос. |
| **Уплотнение** | Сжатие длинного или зашумлённого текста записи до плотной формы перед извлечением аспектов. Исходный текст не меняется (раздел 6.7). |
| **Вопрос** (`needs_review`) | Единый механизм подтверждения: всё, что ниже порога или спорно, программа не решает сама, а спрашивает пользователя (раздел 7). |
| **Дубль** (`duplicate_of`) | Аспект, совпадающий по смыслу с более ранним. Оба остаются в пуле, в базу синтеза идут одним пунктом (раздел 6.11). |
| **Устаревание** (`outdated`) | Пометка мысли или аспекта, которые более новый материал или пользователь признал неактуальными. Ничего не удаляется (раздел 11.1). |
| **Противоречие** (`conflicts_with`) | Два актуальных аспекта одного типа, которые не могут быть верны одновременно. Решает пользователь; до ответа база исходит из предположения модели (раздел 6.12). |
| **Развилка** (ветвление) | Ответ на противоречие «оба верны»: оба направления остаются в базе синтеза, и документы ведут оба (раздел 10.3). |
| **Росток** (`seed`) | Тип контейнера: идея, которая может дорасти до проекта (раздел 3.3). |
| **Операция по требованию** | Действие, которое пользователь запускает сам поверх Фаз 1 и 2: ревалидация, поиск новых составных типов, совет по порогам (раздел 10). |
| **Профиль модели** | Набор настроек одной языковой модели: адрес, модель, ключ, параметры, цены (раздел 13.2). |
| **Ручной режим** (веб-чат) | Работа без API: программа готовит запрос файлом, пользователь переносит его в веб-чат модели и возвращает ответ файлом (раздел 13.5). |
| **Лог рефлексии** | Машиночитаемый журнал пар «предположение системы — решение пользователя» для настройки порогов (раздел 15.3). |
| **Порог** | Число, с которым код сравнивает оценку модели: выше — действие выполняется само, ниже — вопрос. Бывает общим и своим у контейнера (раздел 10.5, 17). |
| **Снимок состояния** | Файл `.system/ui.json`, который программа пишет после каждой команды. Из него плагин берёт всё, что показывает (раздел 18.1). |

## 3. Хранилище

### 3.1 Папки и файлы

Программа работает с одним хранилищем Obsidian. Служебные папки и файлы начинаются с `_` или `.` и не считаются контейнерами. Остальные папки верхнего уровня — контейнеры.

```
Хранилище/
├─ _staging/                    входящие (раздел 4)
│   ├─ архив/                   массовая загрузка — всегда Bootstrap
│   └─ Чат с ИИ/                любая подпапка = источник записей
├─ Книжный клуб/                контейнер верхнего уровня
│   ├─ Книжный клуб.md          карточка контейнера
│   ├─ _записи/                 записи контейнера
│   ├─ Сводный файл.md          документы Фазы 2
│   ├─ Список чтения.md
│   ├─ _аспекты.md              витрина пула аспектов (только чтение)
│   ├─ _база синтеза.md         витрина базы синтеза (только чтение)
│   └─ Встречи онлайн/          под-контейнер: вложенная папка того же устройства
├─ _shared/                     записи, которые относятся к нескольким контейнерам
├─ _unsorted/                   записи без контейнера
├─ _на_проверку/                карантин: записи ждут ответа на вопрос
├─ _исходники/                  входные файлы без изменений
├─ _структура (черновик).md     черновик дерева контейнеров (при массовой загрузке)
├─ open-questions.md            вопросы к пользователю (раздел 7)
├─ _логи/                       журналы для человека (раздел 15)
├─ _веб-чат/                    файлы ручного режима (раздел 13.5)
├─ .system/                     рабочие данные программы
└─ .obsidian/
    ├─ plugins/vtoroy-mozg/     плагин
    └─ snippets/vtoroy-mozg.css цвета (раздел 3.7)
```

Рабочие данные в `.system/`:

| Путь | Что хранит |
| --- | --- |
| `state.json` | Состояние конвейера: принятые файлы, стадии записей и контейнеров, очереди, контрольные суммы текстов (раздел 16.7). |
| `questions.json` | Открытые вопросы к пользователю (раздел 16.6); отвеченные уходят в `_логи/архив вопросов.md`. |
| `data/pools/<id>.json` | Пул аспектов контейнера (раздел 16.3). |
| `data/bases/<id>.json` | База синтеза контейнера; `<id>.prev.json` — прежняя версия для сравнения (раздел 16.4). |
| `vectors/` | Векторы трёх уровней: записи, аспекты, контейнеры (раздел 12.2). |
| `versions/` | Git-зеркало версий баз синтеза и документов (раздел 11.2). |
| `composite_types.json` | Составные типы аспектов, добавленные пользователем (раздел 5.3). |
| `reflection.jsonl` | Лог рефлексии (раздел 15.3). |
| `usage.jsonl` | Журнал обращений к моделям и их стоимости (раздел 14.1). |
| `webchat.json` | Запросы ручного режима: ждущие ответа и уже полученные (раздел 13.5). |
| `ui.json` | Снимок состояния для плагина (раздел 18.1). |
| `lock`, `stop` | Блокировка от второго запуска и флажок «Стоп» из плагина (раздел 11.3). |

Пользователю в `.system` заходить не нужно. Резервная копия — вся папка хранилища вместе со скрытой `.system` плюс `settings.yaml` и файлы ключей из папки программы.

### 3.2 Граф проектов

Контейнеры образуют иерархию: у контейнера может быть родитель (`parent`), у родителя — сколько угодно дочерних. Глубина не ограничена: узлы появляются на любом уровне. Обычно конкретнее всего проработаны под-проекты, а родитель долго остаётся описанием со скоплением мыслей — это нормально.

Кроме родителя, контейнер может применяться в других ветках (`applies_to`). Поэтому структура — граф, а не строгое дерево. Пример: под-проект «Пульсометр» (измерение пульса по камере телефона) входит в проект «Приложение для бега», но применяется и в отдельном проекте «Трекер сна».

```
Приложение для бега
 ├─ записи: мысли, дневник, диалоги с ИИ, ресурсы
 ├─ Пульсометр ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐ applies_to
 │   ├─ записи                         ▼
 │   └─ Сводный файл, другие документы Трекер сна
 └─ Маршруты …                          └─ записи, документы
Книжный клуб                (самостоятельный проект верхнего уровня)
_unsorted                   (записи без контейнера)
```

Иерархия видна и в папках: дочерний контейнер — вложенная папка родителя. Связь `applies_to` папок не меняет.

Записи без контейнера лежат в `_unsorted`. Это не узел графа: у него нет базы синтеза и документов.

### 3.3 Типы узлов

Поле `type` в карточке контейнера:

| Тип | Значение |
| --- | --- |
| `project` | Проект или под-проект любого уровня. |
| `seed` | Росток: идея, которая может дорасти до проекта. |
| `question` | Открытый вопрос пользователя самому себе. Не путать с вопросами программы к пользователю (раздел 7). |

Тип можно писать по-русски: `проект`, `росток`, `вопрос` — программа приведёт его к стандартному значению.

**Росток → проект.** Когда в ростке накапливается материал, анализ пула (раздел 6.10) может предложить сделать его проектом. При уверенности модели не ниже высокого порога (`high`, 90) программа меняет тип сама, ниже — спрашивает.

**«Тихая смерть» ростков.** Если активный росток не получал новых мыслей дольше `seed_dormancy_days` дней (90; поле `last_modified` карточки), программа спрашивает, актуален ли он: оставить ростком, заморозить (`dormant`) или завершить (`completed`). Проверка идёт в конце каждой Фазы 1 по дате, без обращения к модели.

### 3.4 Содержимое контейнера

У каждого контейнера, на любом уровне, одинаковый набор:

- **Карточка** `Название.md` — свойства в YAML-шапке (раздел 16.1) и текст пользователя под ними. В тексте программа меняет только служебный блок между строками `<!-- обновляется программой: начало -->` и `<!-- обновляется программой: конец -->`: число записей, ссылки на общие записи из `_shared`, на документы и витрины.
- **Записи** в `_записи/` — мысли, дневник, диалоги с ИИ, ресурсы, вопросы к себе, ручные правки документов. Вид записи — поле `content_type`: `thought` (мысль), `diary` (о прожитом: что делал, что случилось), `resource` (ссылка или материал для изучения), `question` (вопрос к себе), `ai_dialogue` (диалог с ИИ, раздел 4.2), `product_edit` (ручная правка документа, раздел 8.5); модель может предложить и другое короткое слово. Вид записи не меняет пути обработки: все записи проходят одни и те же шаги.
- **Общие записи** — записи, которые относятся и к этому, и к другим контейнерам. Физически лежат один раз в `_shared/`, а карточка каждого контейнера ссылается на них. Правка не нужна в нескольких местах, рассинхрона копий нет. Аспекты общей записи попадают в пулы всех её контейнеров, и у каждого контейнера своя база синтеза.
- **Документы** Фазы 2 — «Сводный файл» и дополнительные (раздел 8).
- **Витрины** `_аспекты.md` и `_база синтеза.md` — пул и база синтеза в читаемом виде, с цветной подписью источника у каждой мысли. Только для чтения: программа переписывает их после каждой сборки.

Пул аспектов, база синтеза и векторы контейнера лежат в `.system`.

Дневник — не особый вид записи со своим конвейером. Записи о прожитом проходят те же шаги, что и остальные, а дневник как документ модель пишет в Фазе 2, если в базе синтеза есть аспекты опыта (`experience`, раздел 5.2). Обязательного дневника нет ни у контейнера, ни у хранилища.

### 3.5 Статус контейнера

Поле `container_status`:

| Статус | Значение |
| --- | --- |
| `active` | В работе (по умолчанию). |
| `dormant` | Заморожен. Записи по-прежнему раскладываются сюда; ростки с этим статусом не проверяются на «тихую смерть». |
| `completed` | Завершён: итог зафиксирован. Работа не блокируется — доработки возможны. В «Сводном файле» модель обязательно выделяет раздел «Итоговый результат» отдельно от текущего живого описания. |

По-русски тоже можно: `в работе`, `заморожен`, `завершён` и близкие формы.

### 3.6 Что правится руками

Принцип: поле можно править напрямую, если оно **не вычислено моделью**. Организационные данные — названия, связи, статусы, цвета — принадлежат пользователю. Вычисленные данные — пулы, базы синтеза, оценки — меняются только через новый вход или ответ на вопрос. Метафора: пользователь — директор депо. Он нанимает сотрудников (выбирает модели для шагов), перекрашивает вагоны и меняет расписание, но не перестраивает топку на ходу и не переводит стрелки в обход машиниста: подаёт новое топливо (запись) или отвечает на вопросы машиниста.

Программа замечает ручные правки в начале каждой Фазы 1 и применяет их; итог пишется в журнал изменений с пометкой «пользователь».

**Карточка контейнера:**

- `type` — проект, росток или вопрос;
- `parent` — родитель в виде `[[Название]]`, пусто — верхний уровень; папка переедет сама;
- `applies_to` — с какими ещё контейнерами связан;
- `color` — цвет;
- `container_status` — статус (раздел 3.5);
- `description` — описание; программа опирается на него, решая, что сюда относится;
- `thresholds` и `style` — свои пороги (раздел 10.5) и стиль документов (раздел 8.3). Их удобнее менять во вкладке «Контейнер» панели;
- текст под свойствами — кроме служебного блока.

**Переименование.** Название контейнера — имя его карточки. Переименуйте файл (`Книжный клуб.md` → `Клуб чтения.md`) — папка переименуется сама, ссылки `[[…]]` обновятся. Папку отдельно переименовывать не нужно: программа вернёт ей имя карточки.

**Новый контейнер вручную.** Заметка с названием контейнера и свойством `type` (без `id`). Родитель — из `parent` или папка, в которой лежит заметка. В начале следующей Фазы 1 программа выдаст контейнеру `id`, папку, цвет и недостающие поля.

Если карточку контейнера удалить, его записи переедут в `_unsorted` с предупреждением. Так делать не стоит: проще поставить статус.

**Запись:**

- `container` — перенести запись в другой контейнер. Программа переносит файл и аспекты и записывает в лог рефлексии, что её раскладка оспорена (раздел 10.2);
- `also_in` — запись нужна и в других контейнерах: она переедет в `_shared`, её аспекты добавятся в их пулы;
- `conflicts_with` — отметить, что запись спорит с другой: `[[название записи]]`. Такие пары попадают в базу синтеза отдельным списком и учитываются при синтезе (раздел 6.12);
- `status: outdated` (или `устарела`) — мысль больше не актуальна: все её аспекты помечаются устаревшими. Вернуть — `status: processed`, аспекты восстановятся.

**Нельзя править напрямую:**

- **Текст обработанной записи** (раздел 4.3). Программа хранит контрольную сумму текста. Если текст изменился, она продолжает работать с прежним и спрашивает: сделать из правки новую запись или просто вернуть исходный текст. Пока запись не прошла все шаги (например, ждёт в карантине), правка текста принимается.
- **Пулы аспектов, базы синтеза и витрины** — вычисленный слой, программа пересобирает его сама. Ручная правка конфликтовала бы с пересборкой.
- **Папку `.system`**.

Записи не удаляют: вместо удаления — `status: outdated`.

Легитимных способов повлиять на вычисленное три: (1) новая запись через `_staging`; (2) ответ на вопрос; (3) ручная правка документа Фазы 2 — она становится новой записью и проходит Фазу 1 (раздел 8.5).

### 3.7 Цвета

- Контейнеры верхнего уровня получают цвета из базовой палитры по кругу (десять цветов).
- Дочерние — оттенки цвета родителя: цвет смешивается с белым, тем сильнее, чем больше у родителя уже детей (от 25% до 60%).
- Записи в `_записи/` подсвечиваются цветом своего контейнера.
- Общие записи — средним цветом всех их контейнеров.

Цвет — поле `color` карточки, его можно поменять. Оформление — CSS-фрагмент `.obsidian/snippets/vtoroy-mozg.css`, который программа обновляет после каждой команды. Один раз программа включает его сама (`.obsidian/appearance.json`); если пользователь потом его выключит, настройку больше не трогает.

Свои цвета есть и у источников (раздел 4.2): ими подписаны мысли в витринах.

## 4. Вход: `_staging`

Все записи без исключения — от одиночной мысли до архива за несколько лет — попадают в систему через папку `_staging`. Это постоянный канал: класть файлы можно в любой момент, программа примет их при следующей Фазе 1.

### 4.1 Что можно положить

- **Текстовые файлы** `.txt` и `.md`, без обязательной разметки: короткие заметки, выгрузки из мессенджеров, диалоги с ИИ, дневник за годы, длинный текст вперемешку обо всём. Файлы других форматов программа не читает: она перечисляет их в уведомлении и оставляет в `_staging`. Файлы, чьё имя начинается с `.` или `~`, пропускаются.
- **Куда класть** — от этого зависят источник и режим:

| Место | Источник (`source`) | Режим |
| --- | --- | --- |
| корень `_staging/` | `заметка` | определяется автоматически (раздел 6.2) |
| `_staging/<подпапка>/` | имя подпапки, например `Чат с ИИ` | определяется автоматически |
| `_staging/архив/` | `архив` | массовая загрузка (Bootstrap) |
| `_staging/архив/<подпапка>/` | имя самой вложенной подпапки, например `Telegram` | массовая загрузка |

- **Один файл — одна заметка.** Исключения два: дневник с датами делится на записи по датам (раздел 4.2), а при массовой загрузке классификация делит длинный текст на сегменты по темам (раздел 6.4). В обычном режиме запись остаётся целой, даже если касается нескольких контейнеров: связь с остальными оформляется общими записями (раздел 6.5).

**Приём файла.** Программа читает файл, разбирает служебную шапку, копирует файл без изменений в `_исходники/` под именем `ГГГГ-ММ-ДД имя` (если имя уже начинается с даты, вторая не добавляется) и удаляет его из `_staging`. Пустые подпапки `_staging` убираются, кроме `архив`. Пустой файл тоже сохраняется в `_исходники`, но обрабатывать в нём нечего — об этом будет уведомление. Принятые файлы помечаются контрольной суммой: если после сбоя файл остался в `_staging`, второй раз он принят не будет.

### 4.2 Формат файла

**Кодировка** определяется сама: UTF-8 (с BOM или без) или Windows-1251 — типичный случай старых txt-файлов. Переводы строк приводятся к одному виду.

**Служебная шапка** — необязательные строки в начале файла, до основного текста (программа смотрит первые пять непустых строк):

- строка с датой `дд.мм.гггг` (можно с «г.») — дата записи;
- строка `hint: …` (или `подсказка: …`) — подсказка, куда отнести запись (раздел 4.4).

Понимает программа и YAML-шапку Obsidian: поля `hint` (`подсказка`) и `date`, `created` (`дата`). Ещё две служебные строки пишет сама программа: `content_type: …` — у файлов, которые она создаёт из ручных правок, и `mode: steady_state` (`режим: одна запись`) — у «Новой мысли» (раздел 4.5): такой файл всегда обрабатывается как одна запись.

**Дата записи** определяется по порядку:

1. дата из служебной шапки;
2. если её нет — более ранняя из двух дат файла, создания и изменения. При копировании Windows ставит дату создания в момент копирования, а дата изменения сохраняется — поэтому берётся более ранняя;
3. даты внутри текста — это содержание, а не дата заметки: упоминание «встреча 12.05.2025» не становится датой записи.

**Диалоги с ИИ** размечаются префиксами реплик в начале строки: по умолчанию `я:` и `ИИ:` (настройка `dialogue_markers`, списки префиксов можно расширить). Реплика длится до следующего префикса. Файл, где есть реплики обеих сторон, автоматически получает `content_type: ai_dialogue`. Для остальных файлов вид записи предлагает классификация (раздел 6.4).

**Абзацы.** Код нумерует абзацы, и все дальнейшие ссылки на части текста — номера абзацев. Абзац — блок между пустыми строками; если пустых строк в файле нет, абзац — каждая строка. Строка с префиксом реплики всегда начинает новый абзац. Абзац длиннее 8000 знаков делится по строкам и предложениям — так любой файл можно разбить на порции для модели.

**Источник.** Определяется местом файла (раздел 4.1) и нужен для двух вещей: подписи в витринах (у каждого источника свой цвет) и сдвига порога уплотнения (раздел 6.7). На веса и ранжирование источник не влияет: запись из дневника может оказаться пустой, а случайная мысль — очень содержательной, поэтому приоритет строится на типе аспекта и его ценности (раздел 5.4). Список источников — настройка `sources`: имя, цвет и `compaction_shift` — на сколько пунктов понизить для этого источника порог уплотнения. По умолчанию: `архив` и `заметка` — без сдвига, `Чат с ИИ` — на 20 (диалоги с ИИ обычно многословны). Чтобы завести свой источник, достаточно положить файлы в подпапку с его именем; настройки нужны, только если хочется цвет или сдвиг.

**Дневник по датам.** Файл, где записи начинаются строкой с датой (дневник за годы), делится на несколько записей, каждая со своей датой (настройка `input.split_by_dates`, по умолчанию включена):

- начало записи — строка, в которой только дата: `12.03.2021`, `12.03.21`, `2021-03-12`, `12 марта 2021`; можно с днём недели, временем, словом «г.», заголовком `#` или выделением `**`. Сама строка с датой в текст записи не попадает;
- если таких строк нет — дата в начале длинного абзаца (от 300 знаков) после пустой строки, при условии, что такие абзацы идут по порядку дат (по возрастанию или по убыванию). Дата из абзаца вырезается;
- текст до первой даты: если в шапке файла есть своя дата — это отдельная запись с этой датой; иначе короткий текст (до 200 знаков, обычно заголовок) присоединяется к первой записи, а длинный становится отдельной записью с датой файла;
- не делятся: файлы со служебными строками `content_type` или `mode: steady_state`, диалоги с ИИ и файлы, где дат меньше двух (дата шапки тоже считается);
- каждая часть — отдельная запись с полем `source_part` (номер части и её дата). Исходный файл один и хранится целым в `_исходники/`. Дальше части идут обычным путём, в массовой загрузке их ещё может поделить классификация.

### 4.3 Черновик и неизменяемость

**До Фазы 1 запись — черновик.** Пока файл лежит в `_staging`, его можно свободно править: дописать, исправить опечатку, переформулировать.

**После Фазы 1 текст записи неизменяем.** На запись уже ссылаются аспекты, дубли, противоречия и векторы; незаметная правка задним числом обесценила бы эти связи. Изменить содержание обработанной мысли — значит добавить **новую запись** через `_staging`. В Фазе 1 новая запись может:

- дополнить старую: новые аспекты просто добавляются в пул, совпадающие по смыслу связываются как дубли (раздел 6.11);
- пересмотреть её: старый аспект предлагается пометить устаревшим (`outdated`);
- вступить с ней в противоречие (`conflicts_with`, раздел 6.12).

**Если обработанную запись всё же поправили.** Программа хранит контрольную сумму текста каждой записи. Заметив расхождение, она продолжает работать с прежним текстом и задаёт вопрос (раздел 7):

- «Сделать из правки новую запись» — в `_staging` появляется файл «правка — <запись>» с подсказкой на тот же контейнер и пометкой «одна запись». В нём только изменённое: «Автор добавил или переписал: …» и «Автор убрал: …», по предложениям. Исходный текст записи возвращается из `_исходники`;
- «Просто вернуть исходный текст».

Пока запись не прошла все шаги (например, ждёт ответа в карантине), правка её текста принимается без вопроса.

### 4.4 Подсказки

Подсказка — строка `hint: …` в шапке файла (или поле «Куда отнести» в окне «Новая мысль»). Обычно это название контейнера: существующего или нового. Подсказка не диктует результат, а **сдвигает уверенность** в пользу указанного варианта. Модель оценивает, код решает:

1. Модель (промпт «Классификация») возвращает две оценки: свой выбор контейнера с уверенностью **без учёта подсказки** и отдельно уверенность для варианта из подсказки.
2. Код прибавляет к уверенности варианта из подсказки сдвиг `hint_shift` (15 пунктов) и сравнивает с порогом:
   - если модель и подсказка указывают на одно и то же, берётся бо́льшая из двух оценок;
   - если вариант из подсказки с учётом сдвига проходит порог — запись раскладывается по подсказке, даже если собственная уверенность модели была ниже порога. Для существующего контейнера порог — `classification` (70), для нового — `high` (90);
   - если не проходит даже со сдвигом — подсказка расходится с содержанием. Она не продавливается и не игнорируется: запись уходит в карантин с вопросом по причине `user_hint_mismatch` — «указано X, но по содержанию похоже на Y».
3. Подсказки нет — действует обычное правило порогов (раздел 6.5).

В лог рефлексии попадает «чистая» оценка модели без подсказки — так видно, насколько подсказки на самом деле помогают (раздел 15.3).

### 4.5 «Новая мысль»

Команда плагина «Новая мысль» (кнопка в панели или палитра команд) — самый короткий путь записать мысль. Окно: текст; «Куда отнести» — необязательная подсказка с выбором из существующих контейнеров; дата (по умолчанию сегодня); источник (заметка или любой из `sources`, кроме архива); флажок «Сразу обработать (Фаза 1)», по умолчанию выключен — можно набросать несколько мыслей и обработать их разом. Ctrl+Enter — сохранить.

Плагин сохраняет мысль в `_staging` (или в подпапку источника) файлом `ГГГГ-ММ-ДД ЧЧ-ММ <начало текста>.txt` с шапкой из даты, подсказки и строки `mode: steady_state`. Поэтому такой файл всегда одна запись: он не делится ни по датам, ни на сегменты.

## 5. Аспекты

Аспект — смысловая единица, которую модель извлекает из записи (раздел 6.9). Это не отдельный файл и не блок внутри записи, а запись в пуле аспектов контейнера (`.system/data/pools/<id>.json`, раздел 16.3) со ссылкой на запись-источник; у записи — обратные ссылки `aspect_ids`. На аспектах строятся все вычисления: ценность, дубли, противоречия, ранжирование.

Аспекты — **не то же самое**, что документы Фазы 2. Аспекты — сырьё, документы — написанный по ним текст.

### 5.1 Простые типы (уровень 0)

Список фиксирован:

| Тип | Суть |
| --- | --- |
| `fact` | Констатация произошедшего или существующего, без интерпретации. |
| `observation` | Замеченная деталь или закономерность; проверяется менее строго, чем факт. |
| `hypothesis` | Непроверенное предположение. |
| `idea` | Предложение направления или решения. |
| `conclusion` | Вывод, сделанный на основе предыдущего. |
| `question` | Открытая неопределённость. |
| `plan` | Заявленное будущее действие или намерение. |
| `judgment` | Субъективная оценка или реакция. |

### 5.2 Составные типы (уровень 1)

Составной аспект — связка простых аспектов **одного контейнера** (не обязательно из одной записи), которая образует одно целое. Стартовый список:

| Составной тип | Собирается из |
| --- | --- |
| `experience` (опыт) | `plan` + `fact` + `observation`/`judgment` + `conclusion` |
| `resolved_decision` (обоснованное решение) | `question` + несколько `hypothesis`/`idea` + `conclusion` |
| `open_conflict` (развилка) | два и более `hypothesis`/`idea` одного вопроса, не сходящиеся в общий `conclusion` |

Пример опыта в контейнере «Пульсометр»: план «проверить замер при слабом свете» + факт «при свете ночника пульс прыгал на 15 ударов» + наблюдение «вспышка телефона стабилизирует сигнал» + вывод «включать вспышку автоматически».

Формула состава — не только определение типа, но и рабочий алгоритм отбора. Код заранее отбирает для каждой формулы свободные аспекты подходящих типов (если среди них хотя бы два разных типа) и передаёт этих кандидатов в анализ пула. Решает, складываются ли они в одно целое — про одно событие, вопрос или решение, — модель (раздел 6.10). Сначала модель пробует достроить уже существующий составной той же формулы, затем — собрать новый. Составной, который больше не держится (например, часть его состава устарела), модель может распустить: его части снова становятся свободными.

Кирпичики собранного составного получают статус `in_composite`, а в базу синтеза идёт составной аспект целиком.

**Устаревание внутри составного.** Если простой аспект в составе составного помечается устаревшим, составной получает статус `needs_review`, а контейнер — полный пересмотр при следующей сборке базы: модель достраивает или распускает составной. Тихо неактуальным он не остаётся. В базе синтеза такой составной помечен «на пересмотре».

### 5.3 Новые составные типы

Список составных типов открыт. Модель может предложить новый тип, если замечает повторяющуюся связку простых типов, — но только через вопрос пользователю: с формулой, примером того, как это будет выглядеть, и обоснованием, почему это устойчивый паттерн, а не случайное совпадение. Поиск запускает пользователь (операция «Паттерны», команда `patterns`). Он идёт двумя ступенями, чтобы не гонять модель по всей базе:

1. **Технический этап, без модели.** В пуле каждого контейнера берутся свободные аспекты (`active`, не дубли). Каждый аспект связывается с ближайшими соседями (до шести), если сходство их векторов не ниже `pattern_similarity` (0,8). Связанные группы — кандидаты. Подходят группы из трёх и более аспектов с тремя и более разными типами, набор типов которых не укладывается ни в одну существующую формулу. Берутся до восьми самых крупных групп, по двадцать аспектов в каждой.
2. **Содержательный этап, промпт «Новый составной тип».** Модель получает существующие формулы и группы-кандидаты и решает, есть ли среди них устойчивый паттерн. За один раз — не больше двух предложений, каждое — вопрос пользователю. Отклонённые имена запоминаются и повторно не предлагаются.

Подтверждённый тип записывается в `.system/composite_types.json` и с этого момента участвует в анализе пула наравне со встроенными.

### 5.4 Таблица приоритета

Таблица задаёт порядок групп аспектов в базе синтеза — то есть в каком порядке группы подаются модели при написании документов. Это вторая, независимая ось ранжирования. Первая — содержательная ценность — делит элементы на первостепенные и второстепенные **внутри** каждой группы (раздел 6.10). Таблица не подменяет и не дублирует её: ценный срочный план заметен внутри своей группы, где бы ни стояла сама группа.

Единственный критерий таблицы — устойчивость утверждения: сначала то, что уже случилось или осмыслено до конца, затем то, что менее устоялось.

| Место | Тип |
| --- | --- |
| 1 | `resolved_decision` |
| 2 | `fact` |
| 3 | `experience` |
| 4 | `conclusion` |
| 5 | `observation` |
| 6 | `open_conflict` |
| 7 | `hypothesis` |
| 8 | `plan` |
| 9 | `idea` |
| 10 | `judgment` |
| 11 | `question` |

Новые составные типы, добавленные пользователем, встают сразу после `open_conflict`.

### 5.5 Статусы аспекта

| Статус | Значение |
| --- | --- |
| `active` | Свободный простой аспект: участвует в базе синтеза самостоятельно. |
| `in_composite` | Простой аспект вошёл в составной; в базе синтеза он внутри составного. |
| `outdated` | Устарел: пересмотрен более новым материалом или отмечен пользователем. Остаётся в пуле, в синтезе не участвует. Рядом — чем заменён (`replaced_by`). |
| `needs_review` | Только у составного: часть состава устарела, нужна пересборка. |

Независимо от статуса у аспекта может быть пометка `duplicate_of` — ссылка на более ранний аспект с тем же смыслом (раздел 6.11), оценка ценности `value` и пометка `pinned` — «закреплено пользователем» (раздел 6.13). Устаревают и дубли вместе с основным аспектом. Если устарели все аспекты записи, запись целиком получает `status: outdated`.

## 6. Фаза 1: разбор

Фаза 1 (команда `run`, кнопка «Фаза 1» в панели) превращает новые файлы в разложенные по контейнерам записи, извлекает из них аспекты и пересобирает базы синтеза изменившихся контейнеров. Запускается вручную и может растягиваться на несколько сессий: прерванный прогон продолжается с того же места (раздел 11.3).

### 6.1 Порядок шагов

Каждый прогон идёт в таком порядке:

1. **Проверка модели эмбеддингов.** Если векторы посчитаны другой моделью, они пересчитываются (раздел 12.2).
2. **Ручные правки.** Программа применяет то, что пользователь поменял в карточках и записях: тип, родителя, связи, статусы, перенос записей, новые контейнеры, заведённые вручную (раздел 3.6). Замечает правки текста обработанных записей и задаёт о них вопрос (раздел 4.3).
3. **Ответы на вопросы** из `open-questions.md` (раздел 7.3). Пары «предположение — решение» уходят в лог рефлексии.
4. **Утверждённый черновик структуры**, если пользователь его отметил (раздел 6.3).
5. **Ручные правки документов** Фазы 2 становятся новыми записями в `_staging` (раздел 8.5).
6. **Приём файлов** из `_staging` (раздел 4.1).
7. **Черновик структуры** для новой массовой загрузки — Bootstrap, проход 1 (раздел 6.3). Пока черновик не утверждён, файлы этой загрузки ждут.
8. **Разбор файлов**, от старых к новым по дате записи: классификация (раздел 6.4) и пороги (6.5) создают записи, и каждая сразу проходит свои шаги: уточняющие вопросы (6.6), уплотнение (6.7), векторы (6.8), извлечение аспектов (6.9). Хронологический порядок нужен, чтобы «более новое пересматривает более старое» совпадало с реальной хронологией.
9. **Сборка базы синтеза** для каждого контейнера, в который пришли новые аспекты или где изменились статусы (раздел 6.10), и сравнение с прежней версией (6.13).
10. **«Тихая смерть» ростков** — проверка давно не развивавшихся ростков (раздел 3.3).

В конце прогона программа перерисовывает `open-questions.md`, служебные блоки карточек и цвета, фиксирует версии в git-зеркале и пишет снимок для плагина.

У каждой записи есть стадия: `classified` → `asked` → `compacted` → `embedded` → `done`; запись в карантине — `quarantine` → `quarantine_wait`. У контейнера, чья база устарела, — стадия сборки: `analysis` → `value` → `assemble` → `compare`. Стадии сохраняются после каждого шага, поэтому прерванный прогон продолжает с той же записи и того же шага.

### 6.2 Режим: Bootstrap или Steady-state

Внутри Фазы 1 две разные по природе задачи — но не два разных конвейера:

- **Steady-state** — одна новая запись раскладывается по уже существующей структуре контейнеров. Запись всегда остаётся целой.
- **Bootstrap** — структуры нет или она заведомо неполна. Нужно не только разложить материал, но и обнаружить сами контейнеры, а длинные тексты — поделить на сегменты по темам. Вход здесь обычно не россыпь атомарных мыслей, а длинный связный рассказ или полусвязная мешанина, где границы проектов и связи нужно реконструировать.

Режим определяется до классификации, потому что от него зависит, делить ли текст:

1. **Контейнеров ещё нет** (первый запуск) → всегда Bootstrap.
2. **Файл лежит в `_staging/архив/`** → Bootstrap по явному указанию пользователя.
3. **Файл в другом месте `_staging`** → режим не задан. Его предполагает классификация по объёму и устройству текста: длинный текст без явных маркеров ближе к массовой загрузке, короткая одиночная мысль — очевидный Steady-state. Если уверенность ниже `mode_guess` (70), файл ждёт ответа на вопрос «Как обработать файл»: разделить на части по темам или обработать как одну запись.
4. **Служебная строка `mode: steady_state`** (так сохраняет «Новая мысль») → всегда Steady-state.

Полный Bootstrap в два прохода (с черновиком структуры) идёт при пустом хранилище и для `_staging/архив/`. Если Bootstrap выбран для файла из корня `_staging` (уверенно или после ответа), файл делится на сегменты и раскладывается по существующей структуре — без черновика.

### 6.3 Черновик структуры (Bootstrap, проход 1)

Если раскладывать архив по одному файлу и заводить контейнеры по ходу, структуру зададут первые попавшиеся файлы, и легко появятся дубли — например, «Пульсометр» и «проект про пульс по камере» как два разных контейнера. Поэтому массовая загрузка идёт в два прохода.

**Проход 1.** Промпт «Структура» просматривает весь материал загрузки и предлагает дерево контейнеров: название, тип (`project`, `seed`, `question`), краткое описание, родитель, связи `applies_to`. Если материал не помещается в один запрос, код делит его на части, и каждая следующая часть уточняет уже собранный черновик. Если структура уже есть, черновик показывает её вместе с предлагаемыми изменениями.

Черновик — файл `_структура (черновик).md`: вложенный список строк вида

```
- Приложение для бега (проект) — бег, тренировки, сервис для бегунов <!-- n1 -->
    - Пульсометр (проект) — пульс по камере телефона | применяется в: Трекер сна <!-- n2 -->
- Трекер сна (росток) — идея приложения для анализа сна <!-- n3 -->
```

Вложенность — отступом, тип — в скобках, после тире — описание, после «| применяется в:» — связи через «;». Служебная пометка в конце строки — `<!-- k… -->` у существующего контейнера, `<!-- n… -->` у предложенного: по ней программа узнаёт контейнер после переименования, поэтому связи «применяется в» переживают переименование. Строка без пометки или со скопированной пометкой — новый контейнер.

Пользователь правит черновик одним файлом: переименовывает, переподчиняет (меняет отступ), сливает и удаляет темы (удаляет строку — записи этой темы разложатся по оставшимся), меняет тип и описание. Существующий контейнер из черновика удалить нельзя. Утверждение — галочка «Структура утверждена» в том же файле. Это одна проверка вместо сотен отдельных вопросов.

В начале следующей Фазы 1 программа применяет черновик: создаёт новые контейнеры, переименовывает и переподчиняет существующие, расставляет связи. Утверждённый черновик переезжает в `_логи/` («структура утверждена ГГГГ-ММ-ДД»), а итог — сколько предложено и утверждено, что удалено, добавлено, переименовано — пишется в журнал и в лог рефлексии.

**Проход 2.** Файлы загрузки проходят обычные шаги Фазы 1 по утверждённому дереву, с делением на сегменты, в хронологическом порядке. Новые контейнеры, найденные по ходу, создаются по общему правилу порогов (раздел 6.5).

### 6.4 Классификация

Промпт «Классификация» вызывается для каждого нового файла (или части дневника). На вход модель получает:

- нумерованные абзацы текста (раздел 4.2);
- дату, источник, вид записи, если он уже известен, префиксы реплик для диалогов, подсказку пользователя;
- режим (`bootstrap`, `steady_state` или «не задан»);
- все контейнеры: `id`, название, тип, родитель, описание и краткое содержание — начало «Сводного файла» (до 1200 знаков), а если документов ещё нет — сводку из самых ценных аспектов пула. Когда контейнеров больше `max_containers_in_prompt` (150), список заранее сужается векторным поиском по тексту файла; родители найденных добавляются для контекста.

Модель возвращает:

- **сегменты** — диапазоны абзацев, каждый станет отдельной записью. Делить можно только в Bootstrap; в Steady-state сегмент ровно один и включает все абзацы. Текст сегмента код копирует из исходника дословно;
- для каждого сегмента: основной контейнер — существующий (`id`) или новый (название, тип, предполагаемый родитель, описание) — с уверенностью 0–100 **без учёта подсказки**; уверенность для варианта из подсказки, если она есть (раздел 4.4); альтернативы с уверенностью; дополнительные контейнеры, где запись тоже применима, с уверенностью; вид записи (`content_type`), если он не задан на входе; пометку «запись неполная» (`incomplete`) — мысль без пояснений, которые знает только автор; оценку зашумлённости 0–100 для уплотнения (раздел 6.7); рассуждение (`reasoning`);
- предположение о режиме с уверенностью — если режим не задан.

Если файл не помещается в окно модели, код делит абзацы на порции (окна) детерминированно — так, чтобы после сбоя деление повторилось точно так же. Каждое окно классифицируется отдельно, прогресс сохраняется после каждого окна и после каждой созданной записи: сбой не создаст запись дважды.

Имя файла записи — дата и первые слова текста. Запись получает ссылку на исходник (`source_file`) и, если это часть файла, диапазон абзацев (`segment`).

### 6.5 Применение порогов

Решает код, сравнивая оценки модели с порогами. Пороги берутся того контейнера, куда кладётся запись (свои или унаследованные, раздел 10.5); для нового контейнера — его предполагаемого родителя.

| Случай | Порог | Выше или равно порогу | Ниже порога |
| --- | --- | --- | --- |
| Существующий контейнер | `classification` (70) | запись раскладывается сама | карантин `_на_проверку` и вопрос «Куда отнести запись» |
| Новый контейнер | `high` (90) | контейнер создаётся сам, запись кладётся в него | карантин и вопрос с вариантом «Создать …» |
| Ни один контейнер не подходит | `classification` | запись уходит в `_unsorted` | карантин и вопрос |
| Дополнительный контейнер | `high` | запись становится общей: переезжает в `_shared`, её аспекты добавляются и в этот контейнер | вопрос «Запись нужна и в другом контейнере?» |
| Режим не задан | `mode_guess` (70) | режим принимается | вопрос «Как обработать файл» |

Подсказка сдвигает уверенность своего варианта на `hint_shift` (раздел 4.4); если она расходится с содержанием, запись уходит в карантин по причине `user_hint_mismatch`.

В вопросе «Куда отнести запись» варианты собирает код: выбор модели, вариант из подсказки, предложенный новый контейнер, альтернативы и «Без контейнера». Свободный ответ — название контейнера; если такого нет, создаётся новый проект верхнего уровня, тип можно указать в скобках: «Название (росток)».

Записи без контейнера (`_unsorted`) получают векторы, но не аспекты: аспекты извлекаются, когда запись получит контейнер.

### 6.6 Уточняющие вопросы и карантин

Промпт «Вопросы» вызывается, только если уверенность классификации ниже порога (запись в карантине) или запись помечена неполной. Модель получает текст записи, причину, выбор модели с уверенностью и альтернативами, подсказку и описания контейнеров-кандидатов и формулирует до `max_questions_per_entity` (3) коротких вопросов, по возможности — с вариантами ответа.

- **Неуверенная запись** ждёт в карантине (`_на_проверку`), пока пользователь не ответит, куда её отнести. Уточняющие вопросы помогают ему решить.
- **Уверенная, но неполная** запись идёт дальше по шагам, а вопросы к ней попадают в `open-questions.md`. Ответ становится новой записью в `_staging` со ссылкой на исходную — текст обработанной записи не меняется (раздел 4.3).
- **В Bootstrap** вопросы задаются только записям из карантина; неполные получают `incomplete: true` и идут дальше без вопросов — иначе старый архив породил бы сотни вопросов.

Запись с открытыми вопросами помечена в YAML: `needs_review: true` и `review_reason` (`low_confidence`, `user_hint_mismatch`, `new_container`, `incomplete`).

### 6.7 Уплотнение

Отдельный шаг **до** извлечения аспектов: сжатие длинного или зашумлённого текста до плотной читаемой формы, чтобы извлечение не тонуло в шуме. Извлечение — вычленение смысла из готового текста, уплотнение — сжатие исходно многословного текста. Если смешать оба шага в одном рассуждении, модель одновременно решает «что убрать» и «что выделить», и страдают оба результата. Пример: диалог с ИИ обычно полон повторов, уточняющих вопросов и многословных пояснений.

Нужно ли уплотнение, решается по факту содержания конкретного текста, а не по источнику: короткий диалог по делу уплотнять не нужно, длинную сумбурную мысль — может быть, нужно. Зашумлённость (0–100) оценивает модель при классификации — она уже прочитала весь текст. Код вызывает промпт «Уплотнение», если

```
зашумлённость ≥ compaction − compaction_shift источника
```

(`compaction` — 60; у источника «Чат с ИИ» сдвиг 20, то есть порог 40). Решение и оценка пишутся в лог рефлексии.

Уплотнённая версия сохраняется в той же записи отдельным разделом «Уплотнённая версия (создана программой)» под исходным текстом, в YAML — `compacted: true`. Исходный текст не меняется. Дальше (векторы, извлечение) используется уплотнённая версия. Программа проверяет, что сжатый текст действительно короче исходного.

**Диалоги с ИИ.** Опора — реплики пользователя (`я:`) как первоисточник мысли. Реплики модели (`ИИ:`) учитываются как контекст и повод, а не как самостоятельное содержание. Исключение — предложение ИИ, которое пользователь явно принял («да, так и сделаю»): это уже его позиция, и она сохраняется («Принял предложение ИИ: …»). То же правило действует при извлечении аспектов.

Уплотнение одинаково работает в обоих режимах: в Bootstrap — массово, в Steady-state — точечно.

### 6.8 Векторы и похожие записи

Код (без языковой модели) считает вектор записи — по уплотнённой версии, если она есть. Векторы трёх уровней — записи, аспекты, контейнеры — описаны в разделе 12.

**Бесплатная ревалидация.** В обычном режиме программа ищет среди обработанных записей других контейнеров почти совпадающие по смыслу (сходство не ниже `neighbor_similarity`, 0,88). Если такая находится, возможно, одна из двух разложена неверно — и пользователь получает вопрос «Похожие записи в разных местах»: перенести новую, перенести старую, сделать новую общей или оставить как есть. Это дешёвая проверка старой раскладки, которая идёт побочным эффектом обычной работы (раздел 10.1). В Bootstrap проверка не делается: структура только складывается.

### 6.9 Извлечение аспектов

Промпт «Извлечение» разбирает одну запись на простые аспекты (раздел 5.1). Модель получает текст записи (уплотнённый, если есть), дату, вид записи, название и описание контейнера — и не видит остальной пул: это честное разложение именно этой записи, без оглядки на соседей. Связи между аспектами — дело анализа пула (раздел 6.10).

Аспекты добавляются в пул контейнера записи (и в пулы всех её дополнительных контейнеров) со ссылкой на запись и её датой; для каждого аспекта считается вектор. Запись получает `status: processed` и список `aspect_ids`. Если извлечение прервалось, при повторе остатки прерванной попытки убираются — лишних аспектов не остаётся. Контейнер помечается для пересборки базы синтеза.

### 6.10 Сборка базы синтеза

Для каждого контейнера, в который в этом прогоне пришли новые аспекты или в пуле которого изменились статусы:

**1. Анализ пула** (промпт «Анализ пула»). Один вызов по всему пулу контейнера. Каждый аспект подаётся с датой записи-источника, чтобы отличать новое от старого. Кроме самих аспектов модель получает: формулы составных типов и кандидатов по каждой формуле, отобранных кодом (раздел 5.2); существующие составные; какие аспекты новые в этом прогоне; пары похожих аспектов из векторного поиска (сходство не ниже `duplicate_similarity`, 0,86; до 150 пар); уже решённые пользователем пары, чтобы не предлагать их снова; список записей контейнера. При очень большом пуле код делит его на части.

Модель находит:

- **составные аспекты**: достроить существующий или собрать новый из свободных; распустить составной, который больше не держится. Применяется сразу;
- **дубли** — аспекты, совпадающие по смыслу с уже имеющимися. Связываются сразу (раздел 6.11);
- **устаревшее** — аспекты, которые новый материал пересматривает. Всегда только предложение: вопрос «Новая мысль пересматривает старую?» с уверенностью модели. Устаревает более старое по дате;
- **противоречия** между аспектами одного типа — с предположением, какой верен (раздел 6.12);
- **предложения по структуре**: сделать росток проектом; выделить под-контейнер из группы записей. При уверенности не ниже `high` (90) программа делает это сама, ниже — спрашивает.

**2. Оценка ценности** (промпт «Ценность»). Отдельный вызов. Каждый элемент, который может попасть в базу, — свободные простые аспекты (не дубли) и составные целиком — получает оценку 0–100 в контексте всего контейнера. Ценность одного и того же факта зависит от того, что ещё есть в контейнере, поэтому оценка пересчитывается при каждой сборке. Элементы подаются частями по `max_items_per_value_call` (400). Дубли получают оценку своего основного аспекта.

**3. Фильтр** (код). Элементы с ценностью ниже `value_min` (30) в базу не попадают — но остаются в пуле и в витрине. Закреплённые пользователем (`pinned`) проходят всегда.

**4. Группировка по типу** (код). Противоречия из анализа поднимаются вопросом, только если оба аспекта прошли фильтр. Остальные сохраняются и всплывут, если аспект позже пройдёт фильтр.

**5. Ранжирование внутри группы** (код): ценность не ниже `value_primary` (70) — первостепенное, иначе второстепенное. Закреплённое — всегда первостепенное, отклонённая пользователем альтернатива — всегда второстепенная. Внутри группы — сначала первостепенные, затем по убыванию ценности и по дате.

**6. Порядок групп** (код) — по таблице приоритета (раздел 5.4).

Каждый элемент базы хранит текст, ценность, ранг, дату, все записи-источники (с учётом дублей), для составных — состав, и пометки: «спорит с …», «предположительно уступает», «развилка», «рассмотренная и отклонённая альтернатива», «на пересмотре», «закреплено вами». Отдельным списком идут противоречия между записями, отмеченные пользователем вручную (`conflicts_with`). Формат — раздел 16.4. Витрина `_база синтеза.md` показывает базу в читаемом виде, а её текст коммитится в git-зеркало как версия.

Если пул изменился только организационно (ответ на вопрос о противоречии, устаревание вне составного, восстановление элемента), анализ и оценка ценности не повторяются: код пересобирает базу из уже готовых оценок, без новых обращений к модели.

### 6.11 Дубли и пересмотр мыслей

Модель никогда не пишет новый текст мысли за пользователя и не создаёт «объединённых мыслей». Возможны два случая.

- **Новое меняет старое.** Пример: раньше автор думал, что для запуска клуба хватит 5 000 рублей, пересчитал — нужно 12 000. Он кладёт новую мысль в `_staging`. Анализ пула видит, что её аспект пересматривает старый, и предлагает пометить старый устаревшим. После подтверждения база синтеза пересобирается с новым значением; старая мысль остаётся нетронутой. Если пользователь ответит «оба верны», предложение больше не повторяется.
- **Дубли.** Разные записи говорят одно и то же, ничего не опровергая. Анализ пула с учётом похожих пар из векторного поиска связывает совпадающие аспекты: более поздний получает `duplicate_of` на более ранний. В базу синтеза они идут одним пунктом со ссылками на все записи-источники. Связывание применяется сразу, без вопроса: ничего не теряется, все аспекты и записи остаются на месте. Список связанных пар контейнера копится в одном вопросе «Проверьте связанные дубли»: ошибочную связь можно снять, вписав номер дубля (например, `a12`).

Хочет пользователь свести несколько мыслей в одну — он сам пишет новую мысль. Она проходит Фазу 1 как обычный вход, и дальше работают те же два случая.

### 6.12 Противоречия

Отдельный от устаревания случай: два актуальных аспекта одного типа содержательно противоречат друг другу — не потому что один устарел, а потому что решение ещё не принято или это законно разные направления.

**Обнаружение** — в анализе пула. Сравниваются аспекты одного типа между собой (опыт с опытом, идея с идеей), а не вперемешку. Найденное противоречие сохраняется в пуле, а записи-источники получают взаимные ссылки `conflicts_with`. Вопрос пользователю поднимается, только если оба аспекта прошли фильтр ценности.

**Оптимистичное разрешение.** Вместе с противоречием модель сразу даёт своё предположение: верно первое, верно второе или оба (развилка). Пока пользователь не ответил, база синтеза исходит из этого предположения: предполагаемый проигравший **не удаляется**, а остаётся в базе с пометкой «предположительно уступает», и документы пишутся с учётом этого. Ответ применяется пересборкой базы кодом, без нового обращения к модели; если он совпал с предположением, пересчитывать почти нечего. Предположение и ответ попадают в лог рефлексии.

Варианты ответа:

- **«Верно первое» / «Верно второе»** — другой аспект остаётся в базе как рассмотренная и отклонённая альтернатива (второстепенная). В документе её можно упомянуть, если это ценно для контекста;
- **«Оба верны — это развилка»** — ветвление (раздел 10.3): оба направления остаются в базе с пометкой развилки, и синтез ведёт оба;
- **«Это не противоречие»** — пометка снимается, ссылки `conflicts_with` между записями убираются, и эту пару модель больше не предлагает.

Противоречие можно отметить и вручную: поле `conflicts_with` записи (раздел 3.6). Такие пары идут в базу синтеза отдельным списком «отмечены автором», и синтез их учитывает.

### 6.13 Сравнение с прежней версией базы

Последний шаг сборки — содержательное, а не текстовое сравнение новой базы синтеза с прежней. Код находит элементы, которые выпали из базы или потеряли первостепенность, и отсеивает объяснимые потери: устаревание, подтверждённое пользователем; связывание дублей; вхождение в составной; перенос записи в другой контейнер; отклонённую альтернативу; потерю, уже признанную намеренной. Остальное оценивает промпт «Сравнение версий»: значима ли потеря. Значимая — вопрос «Из базы синтеза выпало важное?»:

- «Так и нужно — потеря намеренная» — элемент заносится в `accepted_losses` пула и при следующих сравнениях не поднимается;
- «Вернуть в базу как первостепенное» — элемент закрепляется (`pinned`): дальше он проходит фильтр и всегда первостепенен.

Пока вопрос открыт, база помечена `needs_review` с причиной «значимая потеря по сравнению с предыдущей версией».

## 7. Вопросы и подтверждение (`needs_review`)

Единый механизм для всех случаев неопределённости. Модель никогда не решает такие вопросы сама: она предлагает, пользователь подтверждает. Пока ответа нет, работа не стоит: запись ждёт в карантине или база синтеза исходит из предположения модели (раздел 6.12), а остальное идёт своим чередом.

### 7.1 Откуда берутся вопросы

| Вид (`kind`) | Когда | Варианты ответа |
| --- | --- | --- |
| `classify` — «Куда отнести запись» | Уверенность ниже порога, новый контейнер ниже высокого порога, подсказка расходится с содержанием (раздел 6.5) | Выбор модели, вариант подсказки, новый контейнер, альтернативы, «Без контейнера»; свободный ответ — название контейнера |
| `mode` — «Как обработать файл» | Режим файла не ясен (раздел 6.2) | Разделить на части по темам / как одну запись |
| `also_in` — «Запись нужна и в другом контейнере?» | Дополнительный контейнер ниже высокого порога | Да / Нет |
| `clarify` — «Уточнение к записи» | Неуверенная или неполная запись (раздел 6.6) | Варианты от модели; свободный ответ |
| `outdated` — «Новая мысль пересматривает старую?» | Анализ пула (раздел 6.11) | Да, старое устарело / Нет, оба верны |
| `conflict` — «Противоречие между мыслями» | Анализ пула, оба аспекта прошли фильтр (раздел 6.12) | Верно первое / второе / развилка / не противоречие |
| `dup_fix` — «Проверьте связанные дубли» | Анализ пула связал дубли (раздел 6.11) | Все связи верны; свободный ответ — номера ошибочных дублей |
| `structure_seed` — «Росток дорос до проекта?» | Анализ пула, уверенность ниже высокого порога | Да / Нет |
| `structure_sub` — «Выделить под-контейнер?» | Анализ пула, уверенность ниже высокого порога | Да / Нет; свободный ответ — другое название |
| `base_loss` — «Из базы синтеза выпало важное?» | Сравнение версий базы (раздел 6.13) | Потеря намеренная / вернуть как первостепенное |
| `product_loss` — «В новой версии документа пропало важное?» | Сравнение версий документа (раздел 8.4) | Потеря намеренная / вернуть при следующем синтезе / откатить документ |
| `revalidate` — «Похожие записи в разных местах», «Перепроверка: …» | Похожие записи в разных контейнерах (раздел 6.8), глубокая ревалидация (раздел 10.1) | Перенести, сделать общей, оставить как есть |
| `composite_type` — «Новый составной тип аспектов?» | Поиск паттернов (раздел 5.3) | Да, добавить тип / Нет |
| `dormant` — «Росток давно не развивался» | «Тихая смерть» ростков (раздел 3.3) | Актуален / заморозить / завершён |
| `text_changed` — «Изменён текст обработанной записи» | Правка текста после Фазы 1 (раздел 4.3) | Сделать из правки новую запись / вернуть исходный текст |

Особый случай — черновик структуры при массовой загрузке: он утверждается не вопросом, а целиком, одним файлом (раздел 6.3).

Одинаковые вопросы не дублируются: у каждого есть ключ, и повторное предложение того же самого не создаёт второго вопроса. Решения «нет» запоминаются в пуле контейнера (`rejected`), и модель не предлагает то же снова.

### 7.2 Где видны вопросы

- **`open-questions.md`** в корне хранилища — сводный список открытых вопросов по всем контейнерам. Файл перерисовывается в конце каждой команды из машинного реестра `.system/questions.json` (раздел 16.6). У каждого вопроса — номер (`Q12`), заголовок, дата, текст со ссылками на записи и контейнеры, варианты ответа и, если можно, поле свободного ответа. Над вопросами — уведомления программы (например, «черновик структуры ждёт проверки»).
- **Вкладка «Вопросы» панели плагина** — те же вопросы с кнопками вариантов и полем ответа (раздел 18.2).
- **Сама запись** — в YAML `needs_review: true` и `review_reason`, видно при открытии файла. Записи в карантине лежат в `_на_проверку/`.
- **База синтеза и документ** с открытым вопросом о потере тоже помечены `needs_review` и `review_reason`.

### 7.3 Как отвечать

**В `open-questions.md`:**

- вопрос с вариантами — отметить галочкой **ровно один** вариант (`- [x]`; подходит и кириллическая «х»). Если отмечено несколько, программа оставит вопрос открытым и напишет над ним, что не так;
- свободный ответ — после «Ответ:» (можно в несколько строк);
- ответы из файла применяются в начале следующей Фазы 1.

**В панели** ответ применяется сразу (команда `answer`). Если ответ не подошёл, панель покажет почему.

Что делает свободный ответ:

- в «Куда отнести запись» — название контейнера; если такого нет, создаётся новый проект верхнего уровня, тип можно указать в скобках: «Квартира (росток)»;
- в уточняющем вопросе — ответ становится **новой записью** в `_staging` «уточнение — <запись>»: с подсказкой на контейнер исходной записи, пометкой «одна запись» и парами «Вопрос — Ответ». Текст исходной записи не меняется. Новая запись обрабатывается в ближайшей Фазе 1 (при ответе в файле — в том же прогоне);
- в «Проверьте связанные дубли» — номера ошибочных дублей через запятую: связи снимаются;
- в «Выделить под-контейнер?» — другое название под-контейнера.

Ответ, который программа не может применить (например, запись уже удалили), не теряется: вопрос остаётся открытым с замечанием.

### 7.4 После ответа

Каждый применённый ответ:

- записывается в лог рефлексии парой с исходным предположением системы и признаком, совпали ли они (раздел 15.3);
- уходит с текстом вопроса и выбранным ответом в `_логи/архив вопросов.md` — вопросы не удаляются;
- снимает пометку `needs_review` с записи, если других открытых вопросов к ней нет;
- помечает затронутые контейнеры для пересборки базы синтеза. Если менять нужно только порядок и пометки (противоречие решено, элемент закреплён), база пересобирается кодом без обращений к модели.

## 8. Фаза 2: документы

Документы — другая категория, чем аспекты. Аспекты — сырьё, как источники в списке литературы курсовой. Документ — самостоятельный текст, который модель пишет, поняв **всю** базу синтеза контейнера целиком, а не пересказ или склейка аспектов по одному.

- **«Сводный файл»** — обязательный документ: общее описание проекта в текущем состоянии.
- **Дополнительные документы** — состав открытый, его определяет модель по материалу: например, «Финансовая модель», если есть суммы и расчёты; «Дневник», если есть опыт — тогда записи в хронологическом порядке с датами; «План», «Открытые вопросы». Документ ради документа не создаётся.

Структура содержания документов **намеренно не задаётся**: разный материал требует разной формы, жёсткий шаблон мешал бы. Настраивается стиль изложения (раздел 8.3). Выбор набора дополнительных документов не отделён от синтеза: это одна связная творческая задача над одним материалом, поэтому её решает один промпт «Синтез».

### 8.1 Запуск

Фаза 2 запускается вручную для одного контейнера: кнопка во вкладке «Контейнер» панели или команда `synth "Название"`. Без расписания: модель не работает постоянно.

Перед синтезом программа:

1. принимает ручные правки документов (раздел 8.5);
2. проверяет, что база синтеза актуальна. Если в контейнере есть изменения, ещё не собранные Фазой 1, синтез не начинается: «сначала запустите Фазу 1». Если базы ещё нет (в контейнере нет обработанных мыслей) — тоже;
3. сравнивает «подпись» входа — базу, стиль, сведения о контейнере, текущие документы, намеренные потери и просьбы вернуть — с подписью прошлого синтеза. Если ничего не менялось, документы актуальны, и модель не вызывается. Переписать всё равно можно (`--force`; в окне плагина — ответом на вопрос);
4. оценивает запуск и, если он большой, спрашивает подтверждение (раздел 14.4).

### 8.2 Что получает модель

Промпт «Синтез» получает:

- сведения о контейнере: название, тип, статус, описание, родитель и связи;
- стиль изложения (раздел 8.3);
- базу синтеза текстом: группы в порядке приоритета, в каждой — элементы с рангом (`primary`/`secondary`), датой, ценностью, числом записей-источников и пометками («спорит с …», «предположительно уступает (автор ещё не решил)», «развилка: оба направления живы», «рассмотренная и отклонённая автором альтернатива», «на пересмотре»); у составных — их состав; в конце — противоречия, отмеченные автором вручную;
- текущие версии документов, если они есть, — вместе с ручными правками автора;
- потери, признанные намеренными (их не возвращать), и просьбы вернуть пропавшее (обязательно учесть);
- для завершённого контейнера (`completed`) — требование выделить в «Сводном файле» раздел «Итоговый результат».

Главные правила промпта: всё первостепенное должно найти отражение в документах; гипотезы, идеи и планы подаются как гипотезы, идеи и планы, а не как факты; противоречия и развилки показываются честно; из прежних версий сохраняется то, что по-прежнему верно, особенно правки автора; ничего не выдумывается; документы пишутся на языке заметок.

Ответ — обычный текст (Markdown): документы подряд, каждый начинается строкой `=== ФАЙЛ: Название ===`. Программа проверяет, что есть хотя бы один документ, среди них «Сводный файл», названия не повторяются и документы не пустые; иначе просит модель исправить ответ (раздел 13.4).

### 8.3 Стиль

Стиль изложения настраивается на трёх уровнях:

- **общий** — `style.global` в настройках, для всех контейнеров. По умолчанию: «Пиши ясно и по делу, без воды и общих фраз. Сохраняй формулировки автора там, где они точны.»;
- **контейнера** — поле `style` в карточке (или вкладка «Контейнер» панели). Действует и на вложенные контейнеры, если у них нет своего; важнее общего;
- **документа** — поле `style_override` в YAML документа: только для этого документа в этом контейнере.

Модель получает все действующие уровни сразу, с пометкой, какой важнее.

### 8.4 Запись документов и сравнение версий

Для каждого документа, текст которого изменился, программа **до записи файлов** сравнивает прежнюю и новую версии промптом «Сравнение версий» (вид объекта — документ). Модель получает обе версии и уже признанные намеренными потери и перечисляет пропавшее с пометкой, значимо ли оно. Значимая потеря, ещё не признанная намеренной, — вопрос «В новой версии документа пропало важное?»:

- **«Так и нужно — потеря намеренная»** — потеря заносится в `accepted_losses` документа и больше не поднимается. Так пользователь закрывает направление, которое сознательно исключил: не устаревшее, а просто больше не нужное этому документу;
- **«Вернуть при следующем синтезе»** — пропавшее передаётся следующему синтезу как обязательное;
- **«Откатить документ к прежней версии»** — прежний текст берётся из git-зеркала (раздел 11.2).

Затем документы записываются в папку контейнера, по файлу на документ, с YAML-шапкой (раздел 16.5): вид (`summary` — сводный, `supplementary` — дополнительный), дата генерации, по какой сборке базы написан, `style_override` и `accepted_losses` из прежней версии, пометка `needs_review`, если по документу открыт вопрос. Название документа, совпадающее с названием контейнера или начинающееся с `_`, получает приписку «(документ)», чтобы не путаться с карточкой и витринами. Новая версия каждого документа коммитится в git-зеркало.

Документы, которые модель в этот раз не переписала, остаются как есть — ничего не удаляется. Просьбы вернуть пропавшее после синтеза снимаются, контейнер переиндексируется: начало «Сводного файла» становится его представлением для классификации (раздел 6.4).

### 8.5 Ручные правки документов

Документ можно править руками. Правка — не прямое изменение базы синтеза (её руками не правят), а **новый вход**. В начале каждой Фазы 1 (и перед каждой Фазой 2) программа сравнивает каждый документ с его последней версией в git-зеркале. Если они различаются, в `_staging` появляется запись «правка документа — <документ> (<контейнер>)»: с подсказкой на контейнер, видом `product_edit` и только изменёнными строками — «Автор добавил или переписал: …», «Автор убрал: …». Дальше она проходит Фазу 1 как обычная запись: её аспекты попадают в пул, база синтеза пересобирается, и следующий синтез учитывает правку как полноценный источник наравне с прочими.

Сама правка в документе сохраняется: модель получает текущую версию документа с правками и сохраняет их, если они по-прежнему верны.

## 9. Промпты

Все обращения к языковой модели сведены в набор промптов. Каждый промпт — отдельный файл Markdown в папке `prompts/` программы: его можно прочитать и поправить. Одни и те же промпты работают в режиме API и в ручном режиме через веб-чат (раздел 13.5).

### 9.1 Как устроены

**Критерий разделения.** Отдельный промпт — там, где решение принципиально другого рода (классификация, извлечение и синтез текста — разные «головы» рассуждения) или где шаг сам по себе может закончиться вопросом пользователю. Объединяются шаги, которые логически неразделимы (второй бессмыслен без результата первого в одном рассуждении) и вместе укладываются в разумный объём.

**Контекст не урезается.** Ограничение — деньги, а не токены (раздел 14): промпты не ужимаются искусственно, качество разбора важнее объёма. Если материал не помещается в окно модели, код сам делит его на части (раздел 13.4).

**Подстановки.** Переменные части промпта оформлены как `{{имя}}`. Перед отправкой программа проверяет, что для каждой подстановки есть значение; списки и объекты подставляются как JSON.

**Формат ответа.** Промпты, чей ответ разбирает программа, отвечают строго в JSON. Поле `reasoning` идёт первым — решение, записанное после объяснения, точнее — и сразу уходит в журнал рассуждений (раздел 15.2). «Уплотнение» и «Синтез» пишут обычный текст (Markdown). Программа проверяет каждый ответ: разбирается ли он, все ли поля на месте, существуют ли упомянутые `id`, в допустимых ли пределах числа. При ошибке модель получает список замечаний и присылает исправленный ответ (раздел 13.4).

**Язык.** Промпты написаны по-русски. Ответы модели — тексты аспектов, вопросы, документы — на языке заметок.

**Правка промптов.** Промпты можно менять под себя — осторожно: программа ждёт от ответа прежнего формата. При обновлении программы новые версии промптов ставятся поверх, а изменённые пользователем сохраняются в `prompts/_прежние/` (раздел 19.3).

### 9.3 Что делает код, а не модель

Языковая модель не нужна там, где решение детерминировано. Это делает код:

- определение кодировки, даты, разметки диалогов; деление дневника по датам; нумерация абзацев и дословное копирование сегментов;
- применение порогов и сдвига подсказки; создание контейнеров, перенос записей, общие записи;
- векторный поиск: похожие записи, пары возможных дублей, сужение списка контейнеров, группы-кандидаты в новые составные типы;
- предварительный отбор аспектов по формулам составных типов;
- фильтр, группировка и ранжирование по готовым оценкам ценности; порядок групп по таблице приоритета;
- поиск выпавших элементов при сравнении версий базы синтеза и отсев объяснимых потерь;
- статистика решений для совета по порогам и проверка предложенных значений;
- проверка формата каждого ответа модели.

## 10. Операции по требованию

Механизмы поверх основной работы Фаз 1 и 2. Пользователь вызывает их сам, когда решит, что это нужно. Одни бесплатны (организационное действие, без модели), другие тратят обращения к модели — тогда программа заранее показывает оценку (раздел 14.4).

| Операция | Как вызвать | Модель |
| --- | --- | --- |
| Глубокая ревалидация | кнопка «Ревалидация…» панели или «Перепроверить раскладку» во вкладке «Контейнер»; `revalidate` | одно обращение на запись |
| Оспорить раскладку | поле `container` записи | не нужна |
| Ветвление | ответ «Оба верны — это развилка» на вопрос о противоречии | не нужна |
| Поиск паттернов | кнопка «Паттерны»; `patterns` | одно обращение |
| Совет по порогам | «Посоветоваться с ИИ» во вкладке «Контейнер»; `advise` | одно обращение |

### 10.1 Ревалидация

Раскладка, сделанная однажды, со временем может устареть: появились новые контейнеры, у старых уточнились описания, накопился контекст. Перепроверить её можно двумя путями.

**Бесплатная — по соседям.** Идёт сама, побочным эффектом обычной Фазы 1: если новая запись почти совпадает по смыслу с записью из другого контейнера, программа спрашивает, всё ли разложено верно (раздел 6.8). Ни одного лишнего обращения к модели.

**Глубокая — по команде.** Пользователь выбирает один контейнер или все записи сразу. Для каждой обработанной записи, по порядку дат, программа заново вызывает промпт «Классификация» — в обычном режиме, с текущим списком контейнеров и **без подсказки** автора: нужно чистое мнение модели. Текст берётся рабочий (уплотнённый, если есть).

- Модель относит запись к другому существующему контейнеру с уверенностью не ниже его порога `classification` — вопрос «Перепроверка: запись лежит не там?»: перенести, сделать общей (если запись уже лежит в контейнере) или оставить как есть.
- Модель предлагает новый контейнер с уверенностью не ниже `high` — вопрос «Перепроверка: нужен новый контейнер?»: создать его и перенести запись или оставить как есть.
- Иначе раскладка подтверждена, вопроса нет.

Модель ничего не переносит сама — только предлагает. Каждое её мнение пишется в лог рефлексии (`deep_revalidation`), ответ пользователя — рядом.

Это одно обращение к модели на каждую запись, поэтому перед запуском программа показывает число записей, оценку времени и денег и **всегда** спрашивает подтверждение. Без плагина и консоли подтверждают флагом `--yes`; `--count` только считает записи. Прогресс сохраняется после каждой записи: прерванная ревалидация (сбой, кнопка «Стоп») продолжается с того же места при следующем запуске для той же цели.

Когда стоит запускать: структура заметно изменилась (выделились под-контейнеры, росток стал проектом), появились новые контейнеры, или раскладка старых записей вызывает сомнения.

### 10.2 Оспорить раскладку

Бесплатно и без модели: достаточно поменять поле `container` записи — вписать `[[название]]` другого контейнера (раздел 3.6). Пустое поле — запись уходит в `_unsorted`; несуществующий контейнер — предупреждение, запись остаётся на месте.

В начале следующей Фазы 1 программа переносит файл записи, убирает её аспекты из пула прежнего контейнера и добавляет в пул нового (без нового извлечения — аспекты те же), а базы синтеза обоих контейнеров пересобираются. Если запись была без контейнера, её аспекты извлекаются заново.

Перенос попадает в журнал изменений («классификация оспорена правкой YAML») и в лог рефлексии: к исходному предположению модели добавляется решение пользователя с пометкой «не совпало». Так копится статистика ошибок раскладки — совет по порогам видит, сколько записей, разложенных без вопроса, пользователь потом переложил (раздел 10.5).

### 10.3 Ветвление

Иногда две мысли расходятся не потому, что одна ошибочна или устарела, а потому что это законно разные направления, и автор хочет держать оба. Пример: в «Приложении для бега» есть идея продавать приложение разовой покупкой и идея подписки, и выбор пока не сделан.

Программа не создаёт ветки сама и не готовит под них отдельной инфраструктуры. Ветвление — осознанное решение пользователя: ответ «Оба верны — это развилка» на вопрос «Противоречие между мыслями» (раздел 6.12). После такого ответа:

- оба аспекта остаются в базе синтеза на равных, с пометкой «развилка: оба направления живы»; ни один не становится отклонённой альтернативой;
- синтез ведёт оба направления: «Сводный файл» показывает развилку честно, среди открытых вопросов, а не выбирает победителя за автора;
- эта пара больше не поднимается как противоречие.

Модель может и сама предположить развилку, когда находит противоречие; тогда до ответа пользователя оба аспекта тоже идут в базу с этой пометкой.

Когда выбор сделан, достаточно написать об этом новую запись: анализ пула увидит, что новая мысль пересматривает старую (раздел 6.11).

### 10.4 Поиск паттернов

Ищет устойчивые связки разных простых типов аспектов, которые не покрывает ни один существующий составной тип, и предлагает новый составной тип. Как устроен отбор и что происходит после ответа, описано в разделе 5.3. Это одно обращение к модели на все найденные группы; если подходящих групп нет, к модели программа не обращается. Предложения приходят вопросом «Новый составной тип аспектов?»; принятый тип становится постоянным для всех контейнеров, отклонённый больше не предлагается.

Запускать имеет смысл время от времени, когда в контейнерах накопилось много аспектов.

### 10.5 Пороги контейнера и совет модели

**Общие и свои пороги.** Решения, которые принимает код (раздел 6.5), опираются на пороги. Общие задаются в настройках (`thresholds`), но контейнеры бывают разными: для живого проекта с частыми заметками хочется раскладывать смелее, для тонкой темы — спрашивать чаще. Поэтому почти любой порог можно задать контейнеру свой. Свой порог действует на контейнер и все вложенные в него, пока у вложенного нет своего; иначе действует общий. Источник каждого значения — свой, от родителя или общий — виден во вкладке «Контейнер».

| Порог | Ключ | По умолчанию | Что решает |
| --- | --- | --- | --- |
| Раскладка без вопроса | `classification` | 70 | С какой уверенности запись раскладывается сама, ниже — карантин и вопрос |
| Вес вашей подсказки | `hint_shift` | 15 (0–50) | Сколько пунктов уверенности прибавляется варианту из подсказки |
| Высокая уверенность | `high` | 90 | С какой уверенности программа сама создаёт контейнеры и под-контейнеры, делает запись общей, переводит росток в проекты |
| Догадка о режиме файла | `mode_guess` | 70 | С какой уверенности режим файла принимается без вопроса. Только общий: файл ещё не разложен |
| Уплотнение | `compaction` | 60 | С какой зашумлённости запись сначала сжимается (с поправкой источника, раздел 6.7) |
| Минимальная ценность | `value_min` | 30 | Аспекты ценнее этого идут в базу синтеза |
| Первостепенное | `value_primary` | 70 | С какой ценности аспект первостепенный |
| Похожесть для поиска дублей | `duplicate_similarity` | 0,86 | С какой похожести пары аспектов показываются модели как возможные дубли |
| Похожесть соседей | `neighbor_similarity` | 0,88 | С какой похожести записи из разных контейнеров вызывают вопрос о раскладке |
| Похожесть для паттернов | `pattern_similarity` | 0,8 | Насколько близкими должны быть аспекты, чтобы поиск паттернов счёл их связкой |
| Дней до вопроса о ростке | `seed_dormancy_days` | 90 (7–3650) | Через сколько дней молчания росток получает вопрос «ещё актуален?». Только у ростков |

Шкалы: уверенность, зашумлённость и ценность — 0–100, похожесть — 0,5–0,99.

Каким контейнером определяется порог: при раскладке — тем, куда кладётся запись (для нового контейнера — его будущим родителем, для дополнительного — им самим); при уплотнении и поиске соседей — контейнером записи; при сборке базы, поиске дублей, предложениях по структуре и поиске паттернов — контейнером пула.

**Где задаются.** Во вкладке «Контейнер» панели — ползунок и поле для каждого порога; пустое поле — значение родителя или общее (показано серым), «↺» убирает свой порог. Или вручную — поле `thresholds` в карточке контейнера:

```yaml
thresholds:
  classification: 80
  дубли: 0,9
```

Допускаются русские названия (раскладка, подсказка, высокая, уплотнение, ценность, первостепенное, дубли, соседи, паттерны, дремота), запятая в дробях и знак процента («80%»; для шкалы 0–1 «86%» значит 0,86). Непонятный порог или значение вне диапазона пропускается с предупреждением.

Когда подействуют: пороги раскладки и уплотнения — на новых записях; пороги ценности — при следующей Фазе 1 база синтеза пересобирается кодом, без обращений к модели. Изменение своих порогов и стиля попадает в журнал изменений с пометкой «пользователь».

**Совет модели.** Подобрать пороги на глаз трудно, поэтому программа может посоветоваться с моделью. Код сначала собирает статистику решений по этому контейнеру — из лога рефлексии и состояния: сколько записей разложено без вопроса и сколько из них пользователь потом переложил; сколько вопросов о раскладке было и права ли оказалась модель; как часто подсказка расходилась с мнением модели; сколько предложений «запись нужна и здесь» и перестроек структуры принято и отклонено; распределение зашумлённости и ценности (минимум, квартили, медиана, гистограмма), сколько элементов у самых порогов; сколько потерь пользователь вернул в базу и сколько признал намеренными; сколько связей дублей снято вручную; чем кончились вопросы о похожих соседях; для ростка — сколько дней без новых мыслей.

Промпт «Пороги» получает описание контейнера, таблицу порогов (текущее значение, откуда оно, общее значение, допустимый диапазон), эту статистику и её краткое человеческое изложение. Модель отвечает выводом простыми словами и рекомендациями: порог, новое значение и на каких цифрах это основано. Код проверяет каждую рекомендацию (известный порог, значение в диапазоне, `seed_dormancy_days` — только у ростка, без повторов), а советы «оставить как есть» отбрасывает.

Совет **ничего не меняет сам**. Окно «Совет ИИ по порогам» показывает вывод, предложенные изменения «было → станет» с объяснениями (по умолчанию отмечены все) и раскрывающийся список «На чём основан совет». «Применить выбранное» записывает отмеченные значения в поле `thresholds` контейнера; они подействуют со следующей Фазы 1. Последний совет сохраняется и виден во вкладке «Контейнер» («Есть совет ИИ»).

Совет пишется в лог рефлексии (`thresholds_advice`). Когда пользователь потом меняет пороги контейнера, программа добавляет к совету решение: принят целиком, частично или отклонён, и какие именно значения взяты. Так видно, насколько советам модели можно доверять.

## 11. Надёжность

### 11.1 Ничего не удаляется

Программа ничего не стирает из того, что пришло от пользователя или было выведено из этого. Устаревшее, ошибочное и отклонённое помечается и остаётся на месте — история мысли прослеживается всегда.

| Что | Вместо удаления |
| --- | --- |
| Входной файл | Хранится без изменений в `_исходники/` (раздел 4.1) |
| Текст обработанной записи | Не меняется; правка становится новой записью (раздел 4.3) |
| Запись | `status: outdated` — мысль больше не актуальна, её аспекты устаревают (раздел 3.6) |
| Аспект | Статус `outdated` со ссылкой на заменивший, пометка `duplicate_of`, вхождение в составной (раздел 5.5) |
| Проигравшая сторона противоречия | Остаётся в базе синтеза как отклонённая альтернатива (раздел 6.12) |
| Элемент, выпавший из базы | Остаётся в пуле; признанные намеренными потери — в `accepted_losses` (раздел 6.13) |
| Прежние версии документов и баз | Git-зеркало (раздел 11.2); документ можно откатить ответом на вопрос (раздел 8.4) |
| Контейнер | Статус `completed` или `dormant` (раздел 3.5) |
| Отвечённый вопрос | Переносится в `_логи/архив вопросов.md` вместе с ответом (раздел 15) |
| Отказ «нет» на предложение модели | Запоминается, предложение не повторяется (раздел 7) |

Единственное, что пользователь может удалить сам, — карточку контейнера; его записи тогда переезжают в `_unsorted` с предупреждением (раздел 3.6). Удалять файлы записей не нужно: для этого есть `status: outdated`.

### 11.2 Версии

Версии ведутся для того, что программа переписывает целиком: баз синтеза и документов Фазы 2. Остальное версий не требует: записи не меняются после обработки, а история пулов прослеживается по пометкам (раздел 11.1).

Технически это git-зеркало в `.system/versions/`. Git встроен в программу (библиотека dulwich), ставить его отдельно не нужно. В зеркало попадают текстовые версии: для базы синтеза — её витрина (`_база синтеза.md`), для документа — его текст. В конце каждой команды, если что-то изменилось, программа делает коммит «прогон <дата и время>». Без библиотеки программа работает и дальше, только без истории.

Зеркало служит трём целям:

- **сравнение версий документа** — Фаза 2 сверяет новую версию с прежней (раздел 8.4);
- **ручные правки документов** — отличие файла в хранилище от последней версии в зеркале и есть правка пользователя (раздел 8.5);
- **откат** — ответ «откатить документ» возвращает предыдущую версию из зеркала.

Для сравнения баз синтеза программа держит и машиночитаемую прежнюю версию: `data/bases/<id>.prev.json` (раздел 6.13).

### 11.3 Сбои и прерывания

**Сохранение после каждого шага.** Состояние конвейера (`.system/state.json`), вопросы и векторы сохраняются после каждого шага: принятого файла, классифицированной записи, порции большого файла, извлечения, этапа сборки базы синтеза, документа. Фиксированный интервал не нужен: сохранение дешевле одного обращения к модели. Перезапуск после сбоя продолжает с последнего сохранённого шага, а не с начала. Прерванное извлечение не оставляет лишних аспектов: повтор начинается с чистого места. В ручном режиме через веб-чат это же позволяет остановиться в ожидании ответа и продолжить позже (раздел 13.5).

**Остановка.** В плагине — две кнопки:

- «Стоп» — очередь запусков отменяется (кроме быстрых действий без модели — ответов на вопросы и правок YAML), текущий запуск заканчивает шаг, сохраняет всё и останавливается. Плагин оставляет флажок `.system/stop`, программа проверяет его на каждом шаге, перед каждым обращением к модели и во время пауз между повторами;
- «Прервать сразу» — процесс завершается немедленно: текущий шаг не сохранится, всё сделанное до него цело.

В консоли то же делает Ctrl+C (как «Стоп») или закрытие окна. Остановка по бюджету (раздел 14.3) сохраняет всё так же, как «Стоп». После любой остановки панель предлагает «Продолжить (Фаза 1)».

**Блокировка.** Два запуска над одним хранилищем одновременно невозможны: файл `.system/lock` захватывается средствами системы, и второй запуск получает сообщение «Программа уже работает с этим хранилищем в другом окне». Если программа упала, блокировка снимается сама. Плагин выстраивает свои запуски в очередь, поэтому из него такой ситуации не возникает.

**Сбои связи с моделью.** Запрос повторяется при ответе 429 (слишком много запросов), ошибках сервера 5xx, обрыве связи и ответе не в JSON — с паузами 5, 20, 60 и 120 секунд; паузу прерывает «Стоп». Неверный ключ (401, 403) и переполнение окна модели не повторяются: программа останавливается с понятным сообщением (раздел 13.4).

**Файловые операции.** В Windows файл бывает на мгновение занят — Obsidian, антивирусом, облачной синхронизацией. Программа повторяет операцию несколько раз с короткими паузами. Все файлы пишутся атомарно: сначала во временный файл рядом, потом заменой, поэтому сбой посреди записи не оставляет обрезанного файла.

**Неожиданная ошибка** записывается в `_логи/ошибки.log` с подробностями, а из них собирается отчёт для разработчика (раздел 15.4).

## 12. Поиск похожего: эмбеддинги

### 12.1 Зачем

Эмбеддинг — числовой вектор, передающий смысл текста: чем ближе векторы, тем ближе смысл. Векторы считает отдельная модель эмбеддингов, без языковой модели и без денег за каждое решение. Программа пользуется ими там, где нужно быстро найти похожее среди многого:

| Где | Что ищется | Уровень векторов | Порог |
| --- | --- | --- | --- |
| Бесплатная ревалидация (раздел 6.8) | Почти совпадающие записи из других контейнеров (5 ближайших) | записи | `neighbor_similarity` |
| Анализ пула (раздел 6.11) | Пары аспектов — возможные дубли, которые показываются модели | аспекты | `duplicate_similarity` |
| Классификация (раздел 6.4) | Если контейнеров больше `limits.max_containers_in_prompt` (150), в запрос идут ближайшие по смыслу и их родители | контейнеры | — |
| Поиск паттернов (раздел 5.3) | Группы близких аспектов разных типов | аспекты | `pattern_similarity` |

Модель эмбеддингов не зависит от выбора языковой модели: она отдаёт вектор, хранилище векторов его хранит и ищет, знать друг о друге им не нужно. По умолчанию она работает **на этом компьютере**: ей не нужны ресурсы языковой модели, а сырые личные заметки не уходят наружу даже ради поиска. Облачные эмбеддинги — опция (раздел 12.4). Модель нужна только во время запусков (Фаза 1, проверка связи), постоянно она память не занимает.

### 12.2 Хранилище векторов

Векторы трёх уровней:

- **записи** — по рабочему тексту записи (уплотнённому, если есть);
- **аспекты** — по тексту аспекта;
- **контейнеры** — по названию, описанию и началу «Сводного файла» (до 1500 знаков); пока документов нет — по 12 самым ценным аспектам пула. Вектор контейнера обновляется, когда контейнер создаётся или меняется, после сборки его базы синтеза и после Фазы 2.

Хранятся в `.system/vectors/` собственными файлами: по массиву чисел (numpy) на уровень, рядом — список `id` и название модели, которой они посчитаны. Поиск — косинусная близость перебором: для тысяч и десятков тысяч записей это доли секунды. Отдельная векторная база не нужна, и установка на Windows обходится без сборки и лишних зависимостей. Масштаб личного использования далёк от потолка такого решения.

**Смена модели.** Векторы разных моделей несовместимы. Название модели из настроек (`embeddings.model`) служит меткой векторов: если при запуске она другая, программа предупреждает, сколько это займёт, и сама пересчитывает все векторы — записей, аспектов и контейнеров. Смена языковой модели пересчёта не требует.

**Длинные тексты.** Текст длиннее `embeddings.max_chars` (6000 знаков) обрезается для поиска — сама запись не меняется. Если сервер отвечает, что текст не помещается в окно модели, программа укорачивает его вдвое и пробует снова. Тексты уходят пачками по `batch` (16) штук; для своей модели — ещё и не больше 16 000 знаков за запрос, чтобы расчёт на процессоре не упирался в ожидание ответа.

**Сбои.** Нет ответа или ошибка сервера — повтор с паузами 3, 10 и 30 секунд. Если сервер своей модели не запущен, программа запускает его сама (раздел 12.3) и, пока модель загружается, ждёт. Если связаться так и не удалось, программа останавливается и подсказывает, что сделать.

### 12.3 Своя модель на llama.cpp

По умолчанию — **KaLM-Embedding-Gemma3 12B**: многоязычная модель с окном до 32 768 токенов (квантование Q4_K_S, около 6,9 ГБ; 48 слоёв, вектор из 3840 чисел). Работает через `llama-server` из проекта llama.cpp в формате OpenAI (`/v1/embeddings`).

Ставить ничего вручную не нужно. Кнопка «Запустить модель…» (Настройки → Второй мозг → Модели → Эмбеддинги → «Своя модель») открывает окно запуска:

- **что есть у компьютера** — процессор, ядра и потоки, оперативная память (всего и свободно), видеокарты и их память;
- **параметры:** где считать (процессор или видеокарта); сборка llama.cpp для видеокарты; сколько слоёв модели держать на видеокарте (сколько поместится, все или своё число); контекст; квантование KV-кеша; потоки процессора (кнопка «По ядрам»); порт; через сколько минут простоя выгружать модель из памяти; запускать ли сервер самой программе, когда он нужен; папка модели;
- **предупреждения** — не хватает памяти или видеокарта не найдена;
- **что будет скачано** (один раз) и хватит ли места на диске.

«Запустить» (команда `llama start`) скачивает недостающее, запускает сервер в фоне, ждёт, пока модель загрузится в память (до 15 минут на медленном диске), и сама вписывает адрес сервера и название модели в настройки. Ход скачивания виден в панели; «Стоп» прерывает его, следующий запуск докачивает с того же места. Целостность модели проверяется по контрольной сумме.

**Что скачивается:**

| Что | Откуда | Размер |
| --- | --- | --- |
| Модель | Hugging Face, `mradermacher/KaLM-Embedding-Gemma3-12B-2511-GGUF` | около 6,9 ГБ |
| llama.cpp для процессора | GitHub, готовые сборки `ggml-org/llama.cpp` | около 25 МБ |
| llama.cpp Vulkan — для любых видеокарт | там же | около 38 МБ |
| llama.cpp CUDA — для NVIDIA, только Windows | там же, вместе с библиотеками CUDA | около 680 МБ |
| Библиотеки Microsoft Visual C++ | Microsoft, только Windows и только если их нет | около 25 МБ |

На macOS одна сборка (с Metal), на Linux — для процессора или Vulkan. Если `llama-server` уже установлен на компьютере, для расчёта на процессоре годится и он.

**Параметры** (`embeddings.server` в настройках):

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `device` | `cpu` | `cpu` — процессор, `gpu` — видеокарта (во много раз быстрее) |
| `build` | `auto` | Сборка для видеокарты: `auto` — CUDA для NVIDIA, иначе Vulkan; `cuda`; `vulkan` |
| `gpu_layers` | `auto` | Слоёв на видеокарте: `auto` — сколько поместится, `all` — все 48, или число; остальные считает процессор |
| `ctx` | 4096 | Контекст, токенов: самый длинный текст за раз (4096 — около 12–14 тыс. знаков). Длинное программа всё равно обрезает (раздел 12.2), поэтому 4096 обычно хватает |
| `kv_cache` | `f16` | Квантование KV-кеша. Этой модели почти ничего не даёт: каждый текст она читает целиком за один проход и KV-кеш не хранит |
| `threads` | 0 | Потоков процессора; 0 — llama.cpp решит сам |
| `port` | 8081 | Адрес сервера — `http://127.0.0.1:<порт>/v1`; сервер слушает только этот компьютер |
| `sleep_min` | 15 | Через сколько минут простоя выгружать модель из памяти (следующий запрос загрузит её за несколько секунд); 0 — не выгружать |
| `autostart` | `true` | Если сервер не запущен (например, после перезагрузки), программа сама запускает его при Фазе 1 или проверке связи — с сохранёнными параметрами и ничего не скачивая |
| `models_dir` | пусто | Папка модели; пусто — `models/` в папке программы |

**Память.** Сколько займёт сервер с моделью — сама модель плюс рабочий буфер, который растёт с контекстом:

| Контекст, токенов | 2048 | 4096 | 8192 | 16 384 | 32 768 |
| --- | --- | --- | --- | --- | --- |
| Память, ГБ | 7,8 | 8,4 | 9,6 | 12,6 | 20,1 |

На процессоре нужно не меньше 16 ГБ оперативной памяти; если её меньше или выбранный контекст не помещается, окно запуска предупреждает. Чтобы вся модель поместилась на видеокарту, нужно около 8 ГБ видеопамяти; если меньше, часть слоёв остаётся в оперативной памяти — медленнее, но работает.

**Как запускается сервер.** `llama-server -m <модель> --embedding --pooling last --alias <название> --host 127.0.0.1 --port <порт> -c <контекст> -np 1 -b <контекст> -ub <контекст>`, для процессора — ещё `-ngl 0`, для видеокарты — число слоёв, при необходимости — потоки и время простоя. Размер пакета равен контексту не случайно: модель неказуальная и читает текст целиком за один проход, поэтому весь текст должен поместиться в один пакет, иначе сервер отвечает «input is too large».

**Где что лежит** (в папке программы): `models/` — модель; `llama.cpp/<сборка>/` — llama-server и его библиотеки; `llama.cpp/server.json` — запущенный сервер (номер процесса, порт, параметры); `llama.cpp/server.log` — журнал сервера последнего запуска (его можно открыть из настроек).

**Управление.** В настройках видно, скачана ли модель, какие сборки llama.cpp есть и работает ли сервер; «Остановить» освобождает память (программа запустит сервер снова, когда он понадобится); «Перезапустить…» — с новыми параметрами. Команды: `llama status`, `llama start`, `llama stop`, `llama download` (раздел 20).

**Типичные ошибки** — с подсказкой, что делать: порт занят другой программой (выбрать другой порт); видеокарта не найдена (обновить драйвер, выбрать другую сборку или процессор); не хватает памяти (уменьшить контекст); на порту уже работает сервер с этой моделью, запущенный не программой (программа пользуется им, но поменять его параметры не может).

### 12.4 Другой сервер или облако

Своя модель — не единственный вариант:

- **другой локальный сервер** — любой, умеющий `/v1/embeddings` в формате OpenAI (например, свой `llama-server` с другой моделью). В настройках — адрес (`embeddings.base_url`) и название модели (`embeddings.model`); ключ нужен, только если сервер запущен с ключом;
- **облачные эмбеддинги** — `embeddings.mode: cloud`, адрес и модель провайдера, ключ в файле `embeddings_api_key.txt` рядом с программой, цена `price_input` ($ за 1 млн токенов) — для подсчёта расходов и бюджета (раздел 14).

«Проверить связь» посылает модели короткий текст и сообщает, получен ли вектор. При смене модели векторы пересчитываются сами (раздел 12.2).

## 13. Языковые модели и профили

Программа не привязана к модели или провайдеру. Подходит любой сервис с API в формате OpenAI (`/chat/completions`) — облачный или свой сервер на этом компьютере, а без API — ручной режим через веб-чат. Промпты во всех случаях одни и те же. Модель эмбеддингов выбирается отдельно и от этого выбора не зависит (раздел 12).

### 13.1 Режимы

Основной режим — `llm.mode`:

| Режим | Где работает модель | Что важно |
| --- | --- | --- |
| `cloud` — «Облачная модель (API)» | У провайдера, по ключу | Платно — за токены (раздел 14); окно большое; тексты заметок уходят на сервер провайдера |
| `local` — «Локальная модель (на этом компьютере)» | Свой сервер llama.cpp или другой OpenAI-совместимый, на этом компьютере или в домашней сети | Бесплатно, данные никуда не уходят; обычно слабее облачной и с меньшим окном |
| `webchat` — «Вручную через веб-чат» | В любом веб-чате модели; запросы и ответы переносит пользователь | Без API и ключей; медленно, вручную (раздел 13.5) |

Ни один вариант не навязан. Облачная модель — осознанный компромисс: сырые личные мысли уходят на чужой сервер, зато качество выше и окно больше. Ограничение там — деньги, а не размер окна, поэтому промпты не урезаются ради экономии (раздел 9.1). Локальная модель — самый закрытый вариант ценой качества и настройки.

**Свой сервер языковой модели** пользователь запускает сам (в отличие от сервера эмбеддингов, раздел 12.3), например: `llama-server -m модель.gguf -c 16384 --port 8080`, и вписывает в локальный профиль адрес `http://127.0.0.1:8080/v1`. Ключ для адресов этого компьютера и домашней сети (`localhost`, `127.*`, `10.*`, `192.168.*`, `172.16–31.*`, `*.local`) не обязателен — нужен, только если сервер запущен с ключом.

### 13.2 Профили

Настройки модели хранятся в **профилях** (`llm.profiles`). Профилей может быть сколько угодно: две модели одного провайдера, облачная и своя, сильная и быстрая. Работает профиль, выбранный для режима: `cloud_profile` в облачном режиме, `local_profile` — в локальном.

| Поле | В плагине | Смысл |
| --- | --- | --- |
| `id` | — | Короткий код профиля (`p1`, `p2`…), на него ссылаются настройки |
| `name` | «Имя профиля» | Как профиль называется в списках, в «Расходах» и в журнале |
| `kind` | — | `cloud` или `local` |
| `base_url` | «Адрес API» / «Адрес сервера» | Адрес в формате OpenAI |
| `model` | «Модель» | Название модели точно как у провайдера; для llama.cpp — любое |
| `api_key_file` | «Ключ API» / «Ключ» | Файл с ключом рядом с программой (раздел ниже) |
| `temperature` | «Температура» | 0–2, по умолчанию 0,2: ниже — ответы стабильнее |
| `max_input_chars` | «Предел запроса, знаков» | Длиннее — материал делится на части (раздел 13.4). По умолчанию 300 000 (≈ 100 тыс. токенов) у облачного, 40 000 у локального; для своего сервера — около 3 знаков на токен окна |
| `max_tokens` | «Предел длины ответа (токенов)» | Пусто — как у провайдера |
| `timeout_sec` | «Ожидание ответа, секунд» | 600 у облачного, 1800 у локального |
| `json_mode` | «Режим JSON» | Включить, если сервер умеет `response_format: json_object` — меньше ошибок формата |
| `extra` | «Особые параметры запроса» | Добавляются в запрос как есть, например `{"thinking": {"type": "disabled"}}` |
| `prices` | цены, $ за 1 млн токенов | Только у облачных: вход, вход из кэша, выход (раздел 14.2) |
| `budget_month` | «Лимит профиля в месяц, $» | Только у облачных: свой лимит поверх общего бюджета (раздел 14.3) |

**Ключи** хранятся не в хранилище и не в `settings.yaml`, а в отдельных файлах рядом с программой: у первого профиля — `api_key.txt`, у новых — `api_key_<id>.txt`. Так ключ не попадает в синхронизацию и резервные копии заметок, а у каждого профиля свой файл — ключ одного провайдера не уйдёт на чужой адрес. В плагине ключ вводится в поле, которое не показывает его целиком, и сохраняется в файл программой. Копия профиля по умолчанию пользуется тем же файлом; кнопка «Отдельный ключ» заводит ему свой.

В плагине (Настройки → Второй мозг → Модели): «Режим», основной облачный и локальный профиль, «Профиль для правки» с полями выбранного профиля, кнопки «＋ Облачный», «＋ Локальный», «Копия» и удаление профиля.

### 13.3 Модели для отдельных шагов

Каждому шагу (промпту) можно отдать свой профиль или веб-чат — `llm.roles`, в плагине «Модели для отдельных шагов». Например, «Синтез» — самой сильной модели, частую «Классификацию» — быстрой или своей на llama.cpp, а «Вопросы» — веб-чату:

```yaml
llm:
  roles: {"Синтез": "p2", "Классификация": "p3", "Вопросы": "webchat"}
```

«Как основная» (нет строки в `roles`) — шаг работает на профиле основного режима. В режиме веб-чата профили нужны, только если отдельным шагам отданы свои модели. Расходы ведутся по профилю, который фактически ответил (раздел 14).

### 13.4 Обращение к модели

**Подготовка.** Программа подставляет в промпт переменные (раздел 9.1) и, если запрос шага длиннее предела, делит материал на части. Делятся три шага с длинным материалом: «Структура» — файлы загрузки по частям, каждая часть уточняет черновик; «Классификация» — абзацы длинного файла окнами; «Анализ пула» — аспекты пула частями. Предел — у профиля, который отвечает на шаг (или у веб-чата, `llm.webchat.max_input_chars`); на материал идёт предел за вычетом запаса под задание и списки (около 40–60 тыс. знаков, для небольших пределов — половина). «Ценность» оценивает элементы порциями не больше `limits.max_items_per_value_call` (400).

**Перед обращением** программа проверяет бюджет (для облачного профиля, раздел 14.3) и флажок «Стоп»; пока модель думает, плагин показывает «Ждём ответа модели: <время> · <шаг> · <профиль>».

**Проверка ответа.** Каждый ответ разбирается и проверяется (раздел 9.1). Если что-то не так, программа продолжает тот же диалог: отправляет модели её ответ и список замечаний и просит прислать исправленный целиком. Таких попыток — `llm.max_format_retries` (2), то есть всего три ответа; потом программа останавливается и называет ошибки.

**Обрыв по длине.** Если ответ оборвался по пределу длины (`finish_reason: length`), модель просят прислать его заново короче. Для «Синтеза» это бессмысленно — документ нельзя писать короче по требованию, — поэтому программа сразу останавливается и советует увеличить «Предел длины ответа» профиля или очистить его.

**Ошибки связи и сервера** (раздел 11.3): при 429, 5xx, обрыве связи и ответе не в JSON — повторы с паузами 5, 20, 60 и 120 секунд; если свой сервер не отвечает вовсе, программа долго не ждёт и подсказывает проверить, запущен ли он и верен ли адрес. Неверный ключ (401, 403) — остановка с подсказкой, какой профиль поправить. Переполнение окна модели — остановка с советом: для делящихся шагов уменьшить «Предел запроса», для остальных — отдать шаг профилю с окном побольше; своему серверу llama.cpp можно дать окно больше ключом `-c`.

**Учёт.** Каждое обращение записывается в журнал расходов: шаг, профиль, модель, токены, время и стоимость (раздел 14.1). Если провайдер не сообщил токены, они оцениваются по числу знаков; у llama.cpp токены и кэш берутся из его отчёта о времени. Поле `reasoning` ответа уходит в журнал рассуждений (раздел 15.2), название модели — в лог рефлексии (раздел 15.3).

**Проверка связи** («Проверить связь», команда `check`) проверяет хранилище, промпты и историю версий, посылает каждой используемой модели короткий запрос с ответом в JSON и модели эмбеддингов — короткий текст, и сообщает, кто отвечает и за сколько секунд.

### 13.5 Ручной режим через веб-чат

Для тех, у кого нет API: программа готовит запросы файлами, а пользователь переносит их в веб-чат любой модели. Промпты те же, что и для API.

1. На каждом обращении программа кладёт в папку `_веб-чат/` два файла: `001 <шаг> — запрос.md` и пустой `001 <шаг> — ответ.md` — и останавливается. Панель показывает «Ждёт ответа из веб-чата» с кнопками «Открыть запрос» и «Открыть файл ответа».
2. Пользователь копирует в веб-чат всё, что ниже линии «скопировать всё ниже», а ответ модели целиком вставляет в файл ответа и сохраняет.
3. «Продолжить» (или «Продолжить (Фаза 1)») — программа проверяет ответ так же, как ответ по API. Если всё верно, пара файлов уходит в `_веб-чат/готово/`, и работа идёт дальше до следующего запроса. Если нет — вверху файла запроса появляется предупреждение со списком замечаний: их можно отправить модели и заменить ответ исправленным.

Запросы нумеруются по порядку; уже полученные ответы запоминаются (`.system/webchat.json`), поэтому повтор шага после остановки не создаёт нового запроса. Остановка в ожидании ответа ничего не теряет — работа продолжается с того же места (раздел 11.3). Время и «осталось» в этом режиме не показываются: всё зависит от того, когда будет вставлен ответ. Эмбеддинги и в этом режиме считаются как обычно (раздел 12).

## 14. Расходы, бюджет и оценка запуска

Ограничение облачной модели — деньги, а не размер окна (раздел 9.1). Поэтому программа ведёт учёт каждого обращения, держит месячный бюджет и перед большим запуском прикидывает, во что он обойдётся.

### 14.1 Журнал обращений

`.system/usage.jsonl` — по строке на каждое обращение к языковой модели и к модели эмбеддингов (пачка текстов — одно обращение):

| Поле | Что |
| --- | --- |
| `ts`, `run`, `cmd` | Время, запуск и команда (`run`, `synth`, `revalidate`…) |
| `kind` | `llm` или `emb` |
| `prompt` | Шаг — название промпта; у эмбеддингов «Эмбеддинги», у проверки связи «Проверка связи» |
| `profile`, `profile_name` | Профиль: `id` и имя на момент обращения |
| `ptype` | Вид: `cloud`, `local`, `webchat` или `fake` (тестовая модель) |
| `model` | Модель |
| `in`, `out`, `cached` | Токены на входе, на выходе и из них вход из кэша провайдера |
| `est` | Токены оценены по числу знаков: провайдер их не сообщил |
| `sec` | Сколько длился ответ |
| `cost` | Стоимость в долларах по ценам на момент обращения |

Токены программа берёт из ответа провайдера, у llama.cpp — из его отчёта о времени. Если провайдер ничего не сообщил, токены оцениваются как число знаков, делённое на 3.

### 14.2 Стоимость

Деньги считаются только у облачных моделей. Цены — в профиле (`prices`, $ за 1 млн токенов), у облачных эмбеддингов — `embeddings.price_input`:

стоимость = (вход − вход из кэша) × цена входа + вход из кэша × цена кэша + выход × цена выхода

Цена кэша не задана — кэш считается как обычный вход. Цены лежат в `settings.yaml`, а не в отдельной базе: их видно и можно поправить в одном месте — в профиле (Настройки → Второй мозг → Модели) или прямо во вкладке «Расходы» панели.

Стоимость фиксируется вместе с обращением: смена цен прошлое не переписывает. Пересчёт — явный: после сохранения новых цен панель спрашивает «Пересчитать прошлые обращения?»; команда — `usage --reprice <id профиля | emb | all>`. Журнал до пересчёта сохраняется рядом как `.bak`. Облачные обращения, у которых при записи не было цены, в сводках оцениваются по текущим ценам; если цен нет и сейчас, они идут отдельной строкой «без стоимости» и помечаются звёздочкой.

Локальные модели бесплатны: для них видны токены и время работы. Веб-чат — число обменов. Тестовая модель считается как профиль, к которому привязана, — это нужно для проверок.

### 14.3 Бюджет

- `budget.monthly_usd` — на все облачные модели вместе за календарный месяц; пусто — без бюджета;
- `budget_month` профиля — свой лимит этого профиля;
- `budget.warn_pct` (80) — с какого процента предупреждать.

Перед каждым платным обращением программа сверяет, сколько потрачено за месяц (журнал плюс текущий запуск). С `warn_pct` — одно предупреждение за запуск: в выводе, в панели и уведомлением. При 100% — вопрос «Бюджет исчерпан»: «Продолжить до конца этого запуска» или «Остановить». Если спросить нельзя (запуск без плагина и без консоли), программа останавливается. Остановка по бюджету сохраняет всё так же, как «Стоп» (раздел 11.3); продолжить можно, увеличив бюджет или запустив снова и выбрав «Продолжить».

Бюджет задаётся в настройках (вкладка «Расходы») или прямо во вкладке «Расходы» панели — там же полоса «потрачено из бюджета».

### 14.4 Оценка запуска

До первого обращения к модели программа прикидывает, что предстоит:

- **Фаза 1** — какие шаги и сколько раз будут вызваны: по файлам в `_staging` (с делением дневников по датам) и очереди принятых файлов, по частям длинных файлов, по ожидаемому числу записей и контейнеров;
- **Фаза 2** — синтез по базе синтеза и прежним документам контейнера плюс сравнение версий;
- **ревалидация** — одна классификация на запись.

Средние на одно обращение — токены и время — берутся из журнала для того же шага и профиля, если там хотя бы три обращения; иначе — длина промпта плюс материал и стартовые значения по шагам. Деньги — по ценам профилей, которые отвечают на шаги. Оценка грубая (±50%): сколько записей получится после раскладки, заранее неизвестно.

Перед Фазой 1 и Фазой 2 программа показывает оценку и спрашивает «Запустить?», если запуск большой — больше любого из порогов: `estimate.calls` (30 обращений), `estimate.usd` (0,5 $) или `estimate.minutes` (10 минут). Ревалидация спрашивает всегда (раздел 10.1). `estimate.enabled: false` отключает вопрос, флаг `--yes` пропускает его разово. Если спросить нельзя, Фаза 1 и Фаза 2 запускаются без вопроса, а ревалидация требует `--yes`. Оценку можно получить и отдельно: `estimate run | synth <контейнер> | revalidate [контейнер]`.

### 14.5 Сводка

Вкладка «Расходы» панели (и команда `usage` в консоли):

- итоги за сегодня, этот месяц, прошлый месяц и всё время: деньги, обращения, токены на входе (из них из кэша) и на выходе, время работы моделей;
- бюджет месяца — сколько потрачено и полоса до лимита;
- **модели** — карточка каждого профиля: модель, на каких шагах работает, расход за период, лимит профиля; у облачных — поля цен с кнопкой «Сохранить». Здесь же модель эмбеддингов, а также удалённые профили и прежние модели эмбеддингов, если по ним были обращения;
- **по шагам** — обращения, токены и стоимость по каждому промпту;
- **по дням** — столбики за последние 31 день (стоимость, а без денег — число обращений);
- **последние запуски** — что запускалось и во что обошлось.

Во время запуска вверху панели видно, сколько токенов и денег уже ушло на этот запуск (раздел 18.2).

## 15. Журналы

Три журнала с разными задачами: журнал изменений — что произошло, журнал рассуждений — почему модель так решила, лог рефлексии — насколько её предположения совпадают с решениями пользователя. Журналы для человека лежат в `_логи/` хранилища, машиночитаемые — в `.system/`. Открыть их можно из вкладки «Журнал» панели.

| Файл | Для кого | Что |
| --- | --- | --- |
| `_логи/изменения ГГГГ-ММ.md` | человек | Что, когда и кем изменено (раздел 15.1) |
| `_логи/рассуждения ГГГГ-ММ.md` | человек | Почему модель приняла решения (раздел 15.2) |
| `_логи/архив вопросов.md` | человек | Отвеченные вопросы с ответами (раздел 7.4) |
| `_логи/структура утверждена ГГГГ-ММ-ДД.md` | человек | Утверждённый черновик структуры (раздел 6.3) |
| `_логи/ошибки.log`, `_логи/плагин.log` | разработчик | Неожиданные ошибки программы и плагина (раздел 15.4) |
| `.system/reflection.jsonl` | программа | Лог рефлексии (раздел 15.3) |
| `.system/usage.jsonl` | программа | Журнал обращений и расходов (раздел 14.1) |

### 15.1 Журнал изменений

Общий человекочитаемый журнал всей системы, не только Фазы 1: что и когда изменилось и кем — **пользователь**, **модель** или **программа**. Он дополняет технический git-дифф (раздел 11.2) смысловым пояснением. Новый файл — каждый месяц. Пример строк:

```
- 12.03.2026 14:05 · модель · [[2026-03-12 Пульс по вспышке]] → [[Пульсометр]] (уверенность 84)
- 12.03.2026 14:06 · модель · [[2026-03-12 Пульс по вспышке]]: извлечено аспектов — 4
- 13.03.2026 09:30 · пользователь · [[Книжный клуб]]: classification: общий → 80
- 13.03.2026 09:31 · программа · Фаза 1: готово — 12 обращений, 41 тыс. токенов, $0,03
```

Сюда попадают раскладка и переносы записей, извлечение аспектов, создание и перестройка контейнеров, ручные правки (статусы, связи, пороги, стиль), ответы на вопросы, документы Фазы 2, пересчёт векторов, итог каждого запуска.

### 15.2 Журнал рассуждений

Почему принято то или иное решение: что смущало, какие альтернативы рассматривались. Отдельно не генерируется — заполняется из поля `reasoning` ответов модели (раздел 9.1), в том числе вложенных: у каждого сегмента, дубля, противоречия своё объяснение. Каждая запись — заголовок с временем, шагом, объектом и моделью, ниже — объяснения по пунктам:

```
### 12.03.2026 14:05 · Классификация · файл «пульс.txt» · Z.ai
- **фрагмент 1 → «Пульсометр»**: речь о замере пульса по камере телефона — это ядро под-проекта…
```

Новый файл — каждый месяц.

### 15.3 Лог рефлексии

Служебный слой поверх работы системы. Каждое решение, в котором есть предположение модели, записывается отдельно от результата; когда появляется решение пользователя (ответ на вопрос, ручной перенос, правка порогов), рядом записывается и оно — получается пара «предположение — решение». Цель — накопленная статистика для калибровки порогов: если система стабильно ошибается в одну сторону для какого-то контейнера или источника, это видно, и пороги можно поправить — самому или по совету модели (раздел 10.5).

Формат — JSON Lines, по строке на запись. Предположение: `type: assumption`, `ref` (номер вида `r12`), `kind`, `subject` (о чём), `assumption`, `confidence`, `model` — модель, принявшая решение, чтобы при смене модели статистика не смешивалась, — и дополнительные поля вида. Решение: `type: decision`, тот же `ref`, `kind`, `decision` и `matched` — совпало ли с предположением (`true`, `false` или `partial`).

| Вид (`kind`) | Предположение | Решение пользователя |
| --- | --- | --- |
| `classification` | Контейнер и уверенность **без учёта подсказки**; рядом — подсказка, уверенность её варианта, порог, что сделано (разложено, карантин), кем (модель или подсказка) | Ответ на «Куда отнести запись» или ручной перенос (раздел 10.2) |
| `mode_guess` | Режим файла и уверенность | Ответ «Как обработать файл» |
| `compaction` | Нужно ли уплотнение, зашумлённость, порог и источник | — (статистика зашумлённости) |
| `structure_draft` | Предложенные контейнеры черновика | Сколько утверждено, что удалено, добавлено, переименовано |
| `outdated` | Новый аспект пересматривает старый | Ответ «Новая мысль пересматривает старую?» |
| `conflict` | Противоречие и предположение: верно первое, второе или развилка | Ответ на вопрос о противоречии |
| `seed_to_project`, `subcontainer` | Росток дорос до проекта; нужен под-контейнер | Ответ на вопрос о структуре |
| `base_loss`, `product_loss` | Значима ли потеря при сравнении версий | Ответ на вопрос о потере |
| `composite_type` | Новый составной тип | Принят или отклонён |
| `revalidation_hint` | Похожая запись в другом контейнере и сходство | Перенос или «всё верно» |
| `deep_revalidation` | Контейнер при перепроверке и уверенность | Ответ на вопрос перепроверки |
| `thresholds_advice` | Предложенные значения порогов и текущие | Какие значения приняты, какие нет |

Лог только дописывается и версий не требует: это накопительный служебный слой, а не содержательно меняющаяся сущность.

### 15.4 Ошибки и отчёт для разработчика

**Ошибки программы.** Ожидаемые ситуации — нет ключа, сервер не отвечает, неверный формат настроек — программа объясняет простыми словами и подсказывает, что сделать. Неожиданная ошибка пишется в `_логи/ошибки.log` вместе с командой и полной трассировкой; пользователь видит короткое сообщение: всё обработанное сохранено, повторный запуск продолжит с того же места.

**Ошибки плагина** показываются на месте — красной рамкой «Ошибка в плагине…» с кнопкой «Скопировать отчёт» — и пишутся в `_логи/плагин.log` (больше 512 КБ — прежний журнал становится `плагин.log.old`).

**Отчёт для разработчика** — кнопка «Собрать отчёт» (Настройки → Второй мозг → Дополнительно) или команда плагина «Отчёт для разработчика». В отчёт попадают версии программы, плагина, Obsidian и системы, последние ошибки плагина, конец `ошибки.log` и вывод трёх последних запусков. Ключей API и текстов заметок в нём нет. Отчёт сохраняется в `_логи/отчёт для разработчика.md`, открывается и копируется в буфер обмена — его можно сразу вставить в сообщение.

## 16. Форматы данных

Данные программы — обычные файлы. В хранилище это Markdown-заметки с YAML-шапкой: карточки контейнеров, записи и документы. В `.system/` — JSON-файлы: пулы аспектов, базы синтеза, вопросы, состояние, журналы. Ниже — поля каждого формата. Что из этого можно править руками, сказано в разделе 3.6; остальное ставит и меняет программа.

Ссылки на другие заметки в YAML записываются как `"[[Название]]"`. Рядом с каждой такой ссылкой хранится `id` того же объекта (`parent` и `parent_id`, `container` и `container_id`): по `id` программа узнаёт объект, даже если его переименовали, а по расхождению ссылки и `id` замечает ручную правку. Поля `type` и `container_status` можно писать и по-русски: `проект`, `росток`, `вопрос`; `активный`, `завершён`, `спит`.

### 16.1 Карточка контейнера

```yaml
type: project                  # project | seed | question (раздел 3.3)
id: k004                       # ставит программа; название контейнера = имя файла карточки
color: "#7FB0F5"               # цвет (раздел 3.7)
parent: "[[Приложение для бега]]"   # основной родитель; null — верхний уровень
parent_id: k001
applies_to: ["[[Трекер сна]]"] # где ещё применяется (раздел 3.2)
applies_to_ids: [k007]
container_status: active       # active | completed | dormant (раздел 3.5)
description: "Замер пульса по камере телефона: палец на объективе, вспышка — подсветка."
created: 2026-02-10
last_modified: 2026-03-12      # обновляет программа, когда меняется содержимое контейнера
needs_review: false
review_reason: null
thresholds:                    # свои пороги (раздел 10.5); нет поля — как у родителя или общие
  classification: 75
style: "Короче, списками"      # свой стиль документов (раздел 8.3)
```

| Поле | Что значит |
| --- | --- |
| `type` | Вид узла: проект, росток или вопрос. |
| `id` | Постоянный номер контейнера (`k` и три цифры). Не меняется при переименовании и переносе. |
| `color` | Цвет контейнера; его записи подсвечиваются тем же цветом. |
| `parent`, `parent_id` | Основной родитель — от него зависит, в какой папке лежит контейнер. |
| `applies_to`, `applies_to_ids` | Связи с контейнерами в других ветках, где этот проект применяется. Это не вложенность. |
| `container_status` | Статус: активный, завершён, спит. |
| `description` | Описание. Модель опирается на него, решая, что относится к контейнеру. Если пользователь завёл карточку без описания, программа берёт первый абзац текста. |
| `created`, `last_modified` | Дата создания и дата последнего изменения содержимого (новые мысли, перенос записей, ответы, меняющие пул). По `last_modified` проверяются забытые ростки (раздел 7.1). |
| `needs_review`, `review_reason` | Нужна ли проверка пользователем и почему. |
| `thresholds` | Свои значения порогов. Ключи — имена порогов (раздел 17) или их русские названия. Неверное значение не ломает работу: программа предупреждает и берёт унаследованное. |
| `style` | Свой стиль документов. Наследуется вложенными контейнерами без своего стиля. |

### 16.2 Запись

```yaml
type: entity
id: e00042                     # ставит программа
content_type: thought          # thought | diary | resource | question | ai_dialogue | product_edit | …
source: "заметка"              # источник: подпапка _staging (раздел 4.1)
container: "[[Пульсометр]]"
container_id: k004
shared: false                  # true — запись лежит в _shared
also_in: ["[[Трекер сна]]"]    # другие контейнеры общей записи
also_in_ids: [k007]
created: 2026-03-12            # дата мысли: из шапки, из даты в дневнике или дата файла
source_file: "_исходники/2026-03-12 пульс.txt"
segment: "3-7"                 # какие абзацы исходника; null — весь файл
source_part: "2 из 5 · 12.03.2026"  # только для дневника, разделённого по датам (раздел 4.2)
hint: "Пульсометр"             # подсказка из шапки файла (раздел 4.4)
status: processed              # draft → processed; outdated — мысль устарела
conflicts_with: []             # ручная отметка спора с другой записью: ["[[название записи]]"]
needs_review: false
review_reason: null            # low_confidence | new_container | user_hint_mismatch | incomplete
quarantine: false              # true — запись в _на_проверку и ждёт ответа
incomplete: false              # модель сочла мысль неполной (раздел 6.6)

aspect_ids: [a118, a119]       # ссылки на аспекты в пуле контейнера
```

Под шапкой — текст записи без изменений. Если запись уплотнена, ниже текста добавляется раздел `## Уплотнённая версия (создана программой)` со сжатым текстом: дальше в работу идёт он, а исходный остаётся на месте (раздел 6.7).

Самих аспектов в записи нет — только их номера. Аспекты общей записи лежат в пулах всех её контейнеров. Статус `draft` — запись ещё в работе, `processed` — прошла Фазу 1 и неизменяема (раздел 4.3), `outdated` — устарела: её аспекты не идут в базы синтеза.

### 16.3 Пул аспектов

Файл `.system/data/pools/<id контейнера>.json`. Для чтения человеком — витрина `_аспекты.md` в папке контейнера.

```json
{
  "container_id": "k004",
  "aspects": {
    "a118": {"id": "a118", "type": "fact", "text": "Свет вспышки проходит через палец и даёт видимую пульсацию.",
             "source_entity": "e00042", "date": "2026-03-12", "status": "active", "value": 74, "duplicate_of": null},
    "a131": {"id": "a131", "type": "fact", "text": "Пульсация через палец со вспышкой хорошо видна.",
             "source_entity": "e00057", "date": "2026-03-20", "status": "active", "value": 70, "duplicate_of": "a118"}
  },
  "composites": {
    "c3": {"id": "c3", "composite_type": "experience", "from": ["a101", "a118", "a120"],
           "text": "Попробовал мерить пульс без вспышки — шум; со вспышкой сигнал чистый.",
           "status": "active", "value": 82, "created": "2026-03-12"}
  },
  "conflicts": [
    {"key": "a140|a152", "a": "a140", "b": "a152", "type": "plan", "assumed": "b",
     "assumption": "новее и подробнее", "reasoning": "…", "status": "asked", "decision": null,
     "ref": "r305", "created": "2026-03-21T10:02:11"}
  ],
  "rejected": [{"kind": "duplicate", "a": "a160", "b": "a118"}],
  "accepted_losses": []
}
```

**Простой аспект** (`aspects`):

| Поле | Что значит |
| --- | --- |
| `id`, `type`, `text` | Номер (`a…`), простой тип (раздел 5.1) и формулировка. |
| `source_entity`, `date` | Запись-источник и её дата. |
| `status` | `active`, `in_composite` (вошёл в составной и отдельно в базу не идёт), `outdated` (раздел 5.5). |
| `value` | Содержательная ценность 0–100; пересчитывается при каждой сборке базы. |
| `duplicate_of` | Если аспект — дубль другого: номер исходного. |
| `replaced_by`, `outdated_by`, `status_before` | Если аспект устарел: каким аспектом заменён, откуда пометка (`user` — ответ на вопрос, `entity` — запись отмечена `status: outdated`) и какой был статус до этого — чтобы аспект можно было вернуть. |
| `pinned` | Пользователь вернул аспект после потери: он считается первостепенным при любой оценке. |

**Составной аспект** (`composites`): номер (`c…`), `composite_type` (раздел 5.2), `from` — из каких простых собран, `text`, `status` (`active`; `needs_review` — один из кирпичиков устарел, составной пересмотрит анализ пула; `outdated` — составной распущен, его кирпичики снова `active`), `value`, `created`, `note` — почему составной распущен.

**Противоречия** (`conflicts`): пара аспектов `a` и `b` одного типа, `assumed` — что программа считает верным до ответа (`a`, `b` или `both` — развилка), `assumption` и `reasoning` — почему, `status` (`open` → `asked` → `resolved`; `rejected` — пользователь сказал, что противоречия нет), `decision` — ответ пользователя, `ref` — ссылка на запись в логе рефлексии (раздел 15.3).

**Отклонённые предложения** (`rejected`): пары, о которых пользователь уже сказал «нет», — чтобы не предлагать их снова. Вид: `duplicate`, `outdated`, `conflict`, `seed_to_project`, `subcontainer`.

**Принятые потери** (`accepted_losses`): аспекты, выпадение которых из базы пользователь счёл намеренным (раздел 6.13).

### 16.4 База синтеза

Файл `.system/data/bases/<id контейнера>.json`, рядом — прежняя версия `<id>.prev.json` для сравнения. Для чтения человеком — витрина `_база синтеза.md`.

```json
{
  "type": "synthesis_base",
  "container_id": "k004",
  "container": "Пульсометр",
  "built": "2026-03-21T10:05:40",
  "groups": [
    {"type": "experience", "items": [
      {"id": "c3", "type": "experience", "text": "…", "rank": "primary", "value": 82, "date": "2026-03-12",
       "sources": ["e00031", "e00042"], "dups": [],
       "parts": [{"id": "a101", "type": "action", "text": "…"}, {"id": "a118", "type": "fact", "text": "…"}]}
    ]},
    {"type": "fact", "items": [
      {"id": "a118", "type": "fact", "text": "…", "rank": "primary", "value": 74, "date": "2026-03-12",
       "sources": ["e00042", "e00057"], "dups": ["a131"]}
    ]}
  ],
  "excluded": ["a95"],
  "manual_conflicts": [],
  "needs_review": false,
  "review_reason": null,
  "thresholds": {"value_min": 30, "value_primary": 70}
}
```

| Поле | Что значит |
| --- | --- |
| `built` | Когда собрана. Документы Фазы 2 запоминают это время в `based_on_synthesis`. |
| `groups` | Группы по типам в порядке таблицы приоритета (раздел 5.4). |
| `items` | Пункты группы: первостепенные выше, внутри — по ценности. |
| `rank` | `primary` (ценность не ниже `value_primary` или аспект возвращён пользователем) или `secondary`. |
| `sources`, `dups` | Все записи-источники, включая записи дублей, и номера слитых дублей. |
| `parts` | У составного — его кирпичики. |
| `conflict` | Номера аспектов, с которыми этот пункт спорит. |
| `assumed_loser` | По предположению программы пункт уступает в споре (ответа ещё нет). |
| `fork` | Развилка: оба варианта верны в разных условиях (раздел 10.3). |
| `rejected_alt` | Пользователь выбрал другой вариант; пункт остаётся как отвергнутая альтернатива и всегда второстепенный. |
| `review` | Составной ждёт проверки: один из кирпичиков устарел. |
| `pinned` | Пункт возвращён пользователем после потери. |
| `excluded` | Аспекты ниже порога ценности: в базу не вошли, но остаются в пуле. |
| `manual_conflicts` | Пары записей, отмеченные пользователем в `conflicts_with`. |
| `thresholds` | С какими порогами ценности собрана база. |

Устаревшие аспекты, дубли и кирпичики составных отдельными пунктами в базу не попадают: дубль добавляет источник к исходному пункту, кирпичик виден внутри составного.

Под шапкой — текст документа. Его можно править руками: программа заметит правку и сделает из неё запись (раздел 8.5). `style_override` и `accepted_losses` сохраняются при каждой перезаписи документа.

### 16.6 Вопросы

Файл `.system/questions.json`: счётчик номеров `next` и открытые вопросы `open`. Отвеченный вопрос убирается из `open` и дописывается в `_логи/архив вопросов.md`. Для человека вопросы — в `open-questions.md` и во вкладке «Вопросы» панели (раздел 7.2).

```json
{
  "next": 13,
  "open": {
    "Q12": {"id": "Q12", "kind": "classify", "title": "Куда отнести запись",
            "text": "Запись: [[Замер пульса после пробежки]] (22.03.2026). …",
            "options": [{"label": "«Пульсометр» — вариант модели (уверенность 64)", "value": {"to": "k004"}},
                        {"label": "Без контейнера (unsorted)", "value": {"unsorted": true}}],
            "free_text": true, "free_hint": "Или напишите название контейнера. …",
            "data": {"entity": "e00063"}, "dedup": "classify:e00063", "ref": "r311",
            "created": "2026-03-22T09:15:02", "note": null}
  }
}
```

`kind` — вид вопроса, у каждого вида свой обработчик ответа: `classify` (куда отнести), `mode` (массовая загрузка или одна запись), `also_in` (общая запись), `clarify` (уточнение неполной мысли), `outdated` (устарело ли), `conflict` (противоречие), `structure_seed` и `structure_sub` (росток в проект, под-контейнер), `base_loss` и `product_loss` (потеря в базе и в документе), `composite_type` (новый составной тип), `dormant` (жив ли росток), `revalidate` (итог ревалидации), `text_changed` (изменён текст обработанной записи), `dup_fix` (поправить ошибочное слияние). `options` — варианты, `free_text` — можно ли ответить своими словами, `data` — к чему относится вопрос, `dedup` — ключ, по которому программа не задаёт один и тот же вопрос дважды, `ref` — ссылка на запись в логе рефлексии, куда ляжет ответ, `note` — почему ответ не удалось применить (показывается под вопросом, вопрос остаётся открытым).

### 16.7 Состояние

Файл `.system/state.json` — контрольная точка конвейера. Программа пишет его после каждого шага, поэтому прерванный запуск продолжается с того же места (раздел 11.3).

| Ключ | Что хранит |
| --- | --- |
| `counters` | Счётчики номеров: контейнеры `k`, записи `e`, аспекты `a`, составные `c`, входные файлы `i`, записи лога рефлексии `r`. |
| `items` | Принятые входные файлы: путь в `_исходники`, имя и путь в `_staging`, контрольная сумма, кодировка, источник, дата, подсказка, режим, стадия (`new` → `await_structure` → `ready` → `done`; `await_mode` — ждёт ответа о режиме), часть дневника, созданные записи, ход классификации большого файла по частям. |
| `entity_stage` | Стадия каждой записи: `classified` → `asked` → `compacted` → `embedded` → `done`; карантин — `quarantine` → `quarantine_wait`. |
| `cls` | Итог классификации каждой записи: выбранный контейнер, уверенность, альтернативы, рассуждение, режим, из какого файла. |
| `dirty` | Контейнеры, базу которых надо пересобрать, с причинами и стадией сборки: `analysis` → `value` → `assemble` → `compare`. |
| `new_aspects` | Аспекты, пришедшие с прошлой сборки, по контейнерам. |
| `text_hash` | Контрольные суммы текстов обработанных записей (раздел 4.3). |
| `structure` | Черновик структуры: ждёт ли утверждения и утверждался ли хоть раз. |
| `revalidation` | Очередь незаконченной ревалидации. |
| `restore_requests` | Что пользователь попросил вернуть в документы (ответ на вопрос о потере, раздел 8.4); учитывается при следующей Фазе 2. |
| `synth_sig` | Отпечаток данных последней Фазы 2 по контейнерам: совпал — документы актуальны, модель не вызывается (раздел 8.1). |
| `advice`, `thr_seen` | Последний совет по порогам и последние увиденные пороги и стиль контейнеров — для лога рефлексии (раздел 10.5). |
| `rejected_types` | Новые составные типы, от которых пользователь отказался. |
| `user_outdated`, `auto_outdated`, `auto_cw`, `cw_seen` | Чьи пометки «устарело» и «спорит с» — пользователя или программы: чтобы отличать ручную правку от своей. |
| `css_enabled_once` | Сниппет цветов уже включался один раз (раздел 3.7). |

## 17. Настройки

Все настройки программы — в одном файле `settings.yaml` в папке программы (не в хранилище). Полный список полей с умолчаниями и пояснением у каждой строки — в образце [`settings.template.yaml`](settings.template.yaml); здесь — как устроен файл и что в каких группах.

### 17.1 Файл

- В комплекте программы лежит не сам `settings.yaml`, а образец `settings.template.yaml`. «Установка.bat» (или программа при первом запуске любой команды) копирует образец в `settings.yaml`. Поэтому новая версия, распакованная поверх старой, не затирает настройки (раздел 19.3).
- Ключи API лежат не в настройках, а в отдельных файлах рядом с программой: `api_key.txt`, `api_key_<id>.txt` у других профилей, `embeddings_api_key.txt` у облачных эмбеддингов (раздел 13.2).
- Отсутствующие поля берутся по умолчанию, настройки прежних версий переносятся в нынешний вид при чтении.
- Файл можно сохранить в UTF-8 или в «ANSI» (cp1251) — программа поймёт оба. Путь Windows с обратными слэшами в кавычках (`"D:\Заметки"`) она сама исправляет на прямые.
- Ошибка в YAML не приводит к непонятному сбою: программа называет номер строки и частые причины — отступ клавишей Tab, пропавшая кавычка, двоеточие в тексте без кавычек.

### 17.2 Как правятся

Удобнее всего — в Obsidian: **Настройки → Второй мозг** (раздел 18.3). Окно строится по схеме, которую отдаёт программа: у каждого поля — название, пояснение, пределы и значение по умолчанию. Изменение сохраняется само, через секунду после правки. Программа проверяет все значения вместе и, если всё верно, переписывает `settings.yaml` целиком — с теми же пояснениями, что в образце; прежний файл остаётся в `settings.yaml.bak`. Неверное значение не сохраняется: вверху вкладки появляется «Не сохранено: …» с причиной. Кнопка ↺ у поля возвращает значение по умолчанию. Поиск вверху окна ищет по названиям и пояснениям всех вкладок.

Файл можно править и в любом текстовом редакторе: программа прочитает его при следующей команде.

| `sources` | Источники — подпапки `_staging`: имя, цвет метки, сдвиг порога уплотнения. | «Входящие» | разделы 4.1, 6.7 |
| `style` | `global` — общий стиль документов Фазы 2. | «Документы» | раздел 8.3 |
| `limits` | Пределы запросов: контейнеров в запросе классификации (150), элементов за одну оценку ценности (400), уточняющих вопросов на запись (3). Обычно менять не нужно. | «Дополнительно» | разделы 6.4, 6.6, 6.10 |

### 17.4 Настройки контейнера и документа

Часть настроек можно переопределить для одного контейнера — поля `thresholds` и `style` в его карточке (раздел 16.1; удобнее — во вкладке «Контейнер» панели, раздел 10.5), а стиль одного документа — полем `style_override` в его шапке (раздел 16.5). Свои пороги и стиль наследуются вложенными контейнерами, у которых нет своих. Порог `mode_guess` бывает только общим: режим решается до того, как известно, в какой контейнер попадёт мысль.

Настройки самого плагина — папка программы, Python, уведомления — хранятся отдельно, в файле плагина в хранилище (раздел 18.3).

## 18. Плагин Obsidian

Плагин «Второй мозг» — интерфейс программы внутри Obsidian: кнопки вместо командной строки, окно настроек вместо правки `settings.yaml`, ход запуска, вопросы и расходы на виду. Логики разбора в плагине нет: всё делает Python-программа, плагин запускает её команды и показывает результат. Простые правки — тип и статус контейнера, его пороги и стиль, отметка «Структура утверждена» в черновике — плагин вносит сам через API Obsidian.

### 18.1 Устройство

**Файлы.** Плагин лежит в хранилище, в `.obsidian/plugins/vtoroy-mozg/`: `main.js`, `manifest.json`, `styles.css` и `data.json` — его собственные настройки (раздел 18.3). Ставит его «Установка.bat» (команда `setup`) или команда `install-plugin`: копирует три файла из папки `plugin/` программы, вписывает в `data.json` папку программы и путь к Python окружения `.venv` и включает плагин в списке сторонних плагинов хранилища. При первом открытии хранилища с плагином Obsidian спрашивает, доверяете ли вы автору хранилища, — нужно выбрать «Довериться автору и включить плагины». Если хранилище открыто в ограниченном режиме: Настройки → «Сторонние плагины» → выключить ограниченный режим и включить «Второй мозг». Если Obsidian был открыт во время установки, его нужно перезапустить.

**Запуск команд.** Каждая команда — отдельный процесс в папке программы:

```
python -X utf8 -m brain --json [--ask-stdin] --vault <открытое хранилище> <команда>
```

Плагин всегда работает с хранилищем, открытым в Obsidian, а не с тем, что записано в `settings.yaml`. Команды, которые меняют хранилище, идут строго по одному: следующие ждут в очереди, а такой же запуск, уже стоящий в очереди, второй раз не ставится. Быстрые действия — ответ на вопрос, правка YAML — встают в ту же очередь, чтобы не столкнуться с запуском. Команды, которые хранилище не меняют, — проверка связи, проверка обновлений, чтение и сохранение настроек, состояние своей модели — идут параллельно. Сама программа тоже не даёт двум командам работать с одним хранилищем: вторая, запущенная, например, из консоли, откажется с объяснением (раздел 11.3). Если папка программы не найдена (её перенесли или удалили), панель и настройки говорят об этом и предлагают указать папку.

**Живые строки.** Пока команда работает, программа печатает служебные строки, по которым плагин рисует ход работы:

| Строка | Что передаёт |
| --- | --- |
| `@@PROGRESS` | Этап, номер текущего пункта, сколько всего, название пункта; вложенный этап — например, части большого файла. |
| `@@WAIT` | Программа ждёт ответа модели: шаг, профиль, модель, с какого момента. |
| `@@USAGE` | Расход: каждое обращение и итог запуска — токены и деньги. |
| `@@NOTICE` | Предупреждение по ходу, например «израсходовано 80% бюджета». |
| `@@ASK` | Вопрос посреди запуска (раздел 18.4). |
| `@@RESULT` | Итог в конце: удалось ли, заголовок, счётчики, ошибка. |

**Снимок состояния** `.system/ui.json`. Программа пишет его после каждой команды и по команде `snapshot`; плагин перечитывает его каждые три секунды и сам ничего в хранилище не вычисляет. В снимке:

- версия программы и хранилище;
- статус: число контейнеров, записей, документов и вопросов; стадии записей (обработано, ждут ответа, в очереди) и входных файлов; новые файлы в `_staging`; контейнеры, базы которых ждут пересборки; черновик структуры — ждёт ли он утверждения и утверждался ли хоть раз; запросы веб-чата, ждущие ответа; есть ли незаконченная работа;
- контейнеры: дерево, тип, статус, число записей, документов и вопросов, состояние базы синтеза, действующие пороги и откуда каждый взят (свой, от родителя, общий), стиль;
- открытые вопросы с вариантами;
- общие пороги с описаниями и пределами для ползунков, названия типов и статусов, источники;
- сводка расходов (раздел 14.5) и настройка проверки обновлений;
- ссылки на журналы, предупреждения и сообщения последнего запуска.

### 18.2 Панель

Панель открывается значком мозга на левой ленте или командой «Открыть панель» и по умолчанию встаёт в правую боковую колонку. Вверху — название, состояние («готов», «работает», «ждут ответа: 2», «нет связи с программой»), кнопка ↻ «Обновить состояние» и шестерёнка — настройки плагина. Ниже — пять вкладок.

**Обзор.**

- **При первой загрузке** — мастер из трёх шагов: «Сложите заметки в `_staging`» (сколько файлов уже лежит, «Открыть папку _staging», «Новая мысль»); «Фаза 1 — черновик структуры» — кнопка «Запустить Фазу 1»; «Проверьте черновик и утвердите» — «Открыть черновик» и «Утвердить структуру». Утверждение: плагин сохраняет открытый черновик, ставит в нём галочку «Структура утверждена» и запускает Фазу 1.
- **Дальше** — блоки того, что требует внимания: черновик структуры ждёт утверждения («Открыть черновик», «Утвердить структуру»); ждёт ответа из веб-чата («Открыть запрос», «Открыть файл ответа»); ждут ответа N вопросов («Ответить»); новые файлы в `_staging` («Обработать (Фаза 1)»); обработка не закончена («Продолжить (Фаза 1)»). Если ничего нет — «Всё обработано».
- Кнопки действий: «Фаза 1: обработать новое», «Новая мысль», «Фаза 2: документы…», «Ревалидация…», «Паттерны», «Проверить связь».
- Счётчики: контейнеры, записи, документы, вопросы и строка стадий («обработано 120 · ждут ответа 3 · в очереди 5»).
- Текущая модель и её расход в этом месяце, расход всех моделей, полоса бюджета; ссылка «Расходы →».
- Предупреждения последнего запуска и дерево контейнеров с числом записей; контейнер, база которого ждёт пересборки, отмечен. Щелчок по контейнеру открывает его во вкладке «Контейнер».

**Вопросы.** Карточки открытых вопросов: текст, варианты, поле «Свой ответ», ссылки на запись и контейнер. Ответ применяется сразу (команда `answer`); если идёт запуск — встаёт в очередь («применится после текущего запуска»). Фильтр по контейнеру. Подробнее — раздел 7.3.

**Контейнер.** Выбранный в списке или контейнер открытой заметки (переключатель «по открытой заметке»). Тип и статус — выпадающие списки, плагин пишет их в карточку. Число записей, вопросов, пунктов базы синтеза и аспектов ниже порога ценности; ссылки на витрины пула и базы. Документы контейнера с пометкой «на проверке»; кнопки «Написать документы (Фаза 2)» или «Обновить документы (Фаза 2)» и «Перепроверить раскладку» (ревалидация контейнера, раздел 10.1). Блок «Пороги контейнера» (раздел 10.5) и «Стиль документов» (раздел 8.3).

**Расходы.** Сводка из раздела 14.5: итоги за периоды, бюджет, карточки моделей с ценами, по шагам, по дням, последние запуски. Цены и бюджет правятся прямо здесь; после смены цен плагин предлагает пересчитать прошлые обращения.

**Журнал.** Запуски этого сеанса Obsidian: значок (⧗ в очереди, ▶ идёт, ✓ готово, ✗ ошибка, ■ остановлен), время, длительность, сколько думали модели, токены и деньги, итог и полный вывод программы («вывод программы»). Ссылки на журналы: «Изменения», «Рассуждения модели», «Архив вопросов», «Ошибки», `open-questions.md`.

**Во время запуска** вверху панели — блок хода работы:

- этап и счёт («Разбор файлов: 12 из 80»), вложенный этап, полоса;
- сколько идёт запуск и сколько осталось — по средней скорости этапа, после первого готового пункта (в режиме веб-чата времени нет: модель не ждут);
- «Ждём ответа модели: 0:15 · Классификация · Z.ai» — секундомер, шаг и профиль;
- «Этот запуск» — токены и деньги;
- «В очереди: …» — что запустится следом;
- «Стоп» и «Прервать сразу» (с подтверждением) — раздел 11.3; «Вывод программы».

Итог запуска — всплывающее сообщение Obsidian и строка в «Журнале».

**Строка состояния** внизу окна: без запуска — «Второй мозг» или «Второй мозг · 3 вопроса»; во время запуска — что идёт, счёт, ожидание модели или оставшееся время, длительность. Щелчок открывает панель.

**Узкая колонка.** Панель подстраивается под свою ширину: вкладки переносятся на вторую строку, состояние в шапке — под название, счётчики при ширине до 360 пикселей — по два в ряд.

### 18.3 Настройки

Настройки → Второй мозг. Окно строится по схеме программы (команда `settings`): поля, пояснения, пределы, умолчания и проверка — в программе (раздел 17.2). Работает и в отдельном окне настроек, и в обычном модальном. Вверху — поиск по всем вкладкам.

| Вкладка | Что в ней |
| --- | --- |
| Основное | «Программа»: папка программы, Python, «Проверка связи». «Уведомления Windows». «Обновления»: «Проверять при запуске Obsidian», «Проверить обновления». |
| Модели | «Языковая модель»: режим, профили, «Профиль для правки», «＋ Облачный», «＋ Локальный», «Копия», удаление (раздел 13.2). «Модели для отдельных шагов» (раздел 13.3). «Эмбеддинги (поиск похожего)» с блоком «Своя модель»: что скачано, работает ли сервер, «Запустить модель…», «Остановить», журнал сервера (раздел 12.3). «Проверка связи». |
| Пороги | «Общие пороги» — ползунок и поле у каждого, плюс срок проверки ростков. |
| Входящие | «Источники» («Добавить источник»), «Разметка диалогов», «Делить дневник по датам». |
| Документы | «Общий стиль» документов. |
| Расходы | «Бюджет», «Оценка перед большим запуском», переход к вкладке «Расходы» панели. |
| Дополнительно | «Пределы», «Повторов при ошибке формата», «Предел запроса веб-чата». «Служебное»: «Открыть папку промптов», файл настроек («Показать в папке»), «Собрать отчёт» (раздел 15.4). |

Поля, нужные только при определённом значении другого поля, показываются по условию: например, ключ и цена облачных эмбеддингов — только при «Облачный сервис». У поля, отличного от умолчания, кнопка ↺ яркая; при значении по умолчанию — тусклая. Ключи вводятся в поле, которое их не показывает, и сохраняются в файлы рядом с программой (команда `settings --key`); в окне виден только факт «ключ сохранён».

**Собственные настройки плагина** хранятся в его `data.json`, а не в `settings.yaml`:

| Настройка | По умолчанию | Что значит |
| --- | --- | --- |
| Папка программы | вписывает установка | Где лежат `brain/` и «Установка.bat». |
| Python | пусто | Пусто — Python окружения `.venv`, которое создала установка. |
| Сообщать об окончании долгого запуска | да | Системное уведомление по окончании Фазы 1, Фазы 2 или ревалидации. |
| Долгий запуск — дольше, минут | 2 | 0 — сообщать о любом запуске. |
| Сообщать, когда программа ждёт ответа | да | Например, бюджет исчерпан или нужно подтвердить большой запуск. |
| Только когда Obsidian не в фокусе | да | Выключить — уведомления приходят всегда. |
| Пропущенная версия | — | Версия, которую пользователь решил не ставить (раздел 19.3). |

Уведомления — системные уведомления Windows. Отменённые запуски не сообщаются. Щелчок по уведомлению открывает Obsidian и панель. «Пробное уведомление» → «Показать» проверяет, разрешены ли они; если уведомление не появилось, нужно разрешить уведомления для Obsidian в параметрах Windows (Система → Уведомления).

Команды в палитре Obsidian (Ctrl+P), все с префиксом «Второй мозг:»:

| Команда | Что делает |

**Окна плагина:** подтверждение; выбор варианта — вопрос программы посреди запуска, предложение обновиться, перезапуск Obsidian; выбор контейнера с поиском по названию; «Новая мысль» (раздел 4.5); «Совет ИИ по порогам» (раздел 10.5); итог проверки связи — по каждому пункту отдельно: хранилище, каждая различающаяся модель шагов, эмбеддинги; параметры своей модели эмбеддингов (раздел 12.3).

**Вопросы посреди запуска.** Некоторые решения программа не может принять сама: бюджет исчерпан (раздел 14.3), запуск большой или это ревалидация (раздел 14.4). Тогда она печатает строку `@@ASK` с вопросом и вариантами и ждёт. Плагин открывает окно с вариантами, в блоке запуска пишет «Программа ждёт вашего ответа», при необходимости присылает уведомление и отправляет выбор в стандартный ввод программы. Закрытое окно — отказ. В консоли тот же вопрос задаётся в окне консоли: номер варианта или «д/н». Если спросить нельзя, действует безопасное умолчание — оно указано в разделах 14.3 и 14.4.

Если документы контейнера актуальны, Фаза 2 заканчивается без обращений к модели; плагин спрашивает «Переписать их всё равно?» и при согласии запускает её снова с `--force` (раздел 8.1).

**При запуске Obsidian** (через три секунды) плагин сначала сравнивает плагин в папке программы со своим: если там новее (новую версию распаковали вручную), предлагает установить его и перезапустить Obsidian. Затем, если включена проверка обновлений, ищет новую версию программы на GitHub (раздел 19.3).

### 18.5 Ошибки плагина

- Каждая часть интерфейса рисуется отдельно: шапка панели, каждая вкладка панели, каждый раздел каждой вкладки настроек. Ошибка в одной части не ломает остальные: на её месте появляется красная рамка «Ошибка в плагине (панель, вкладка «Расходы»)» с текстом ошибки, подсказкой и кнопкой «Скопировать отчёт» — версии плагина, программы, Obsidian и системы и ошибка со стеком.
- Необработанные ошибки окна, в стеке которых есть сам плагин, тоже записываются — без всплывающих окон. Ошибки других плагинов и самого Obsidian плагин не трогает.
- Журнал — `_логи/плагин.log` в хранилище; больше 512 КБ — прежний журнал становится `плагин.log.old`. В памяти хранятся последние 30 ошибок; одна и та же ошибка подряд записывается один раз.
- Копирование в буфер обмена работает и из отдельного окна настроек.
- «Отчёт для разработчика» собирает всё это вместе с выводом последних запусков — раздел 15.4.

## 19. Установка и обновление

### 19.1 Установка

**Что нужно.** Windows, Obsidian и интернет на время установки. Python 3.10 или новее — если его нет, установщик поставит его сам. Видеокарта не обязательна. Своя модель эмбеддингов на процессоре требует не меньше 16 ГБ оперативной памяти (раздел 12.3); облачным эмбеддингам это не нужно.

**Порядок.**

1. Хранилище Obsidian — существующее или новое (в Obsidian: «Создать хранилище» или «Открыть папку как хранилище»). Служебные папки программа создаст сама.
2. Архив программы распаковывается в отдельную папку, например `D:\Программы\Второй мозг`. Папка программы не должна лежать внутри хранилища: программа приняла бы свои файлы за заметки.
3. Запускается `Установка.bat`. Он пишет, какой идёт шаг, а при ошибке — что именно не получилось и что сделать:
   - **Python.** Ищет Python 3.10+ (`py`, `python` и обычные папки установки). Если не находит, спрашивает, поставить ли Python 3.12: ставит его только для текущего пользователя Windows, без прав администратора — через winget, а без него — установщиком с python.org.
   - **Окружение.** Создаёт в папке программы окружение `.venv`; повреждённое (например, после переустановки Python) — создаёт заново.
   - **Библиотеки** из `requirements.txt`: PyYAML, requests, numpy, dulwich. Создаёт `settings.yaml` из образца и пустой `api_key.txt`, если их ещё нет.
   - **Команда `setup`** — остальное делает сама программа: убирает `.bat`-файлы прежних версий; находит хранилища Obsidian по его списку хранилищ (сначала открытое сейчас, потом — по времени последнего открытия) и спрашивает, в какое поставить плагин: Enter — первое, номер или путь к папке хранилища (можно перетащить папку в окно); если Obsidian открыт — просит закрыть его; ставит плагин (раздел 18.1) и вписывает папку хранилища в `settings.yaml`; предлагает сразу скачать модель эмбеддингов и llama.cpp — с размерами и предупреждением, если памяти мало («д/н»; можно позже — кнопкой «Запустить модель…»); открывает Obsidian.
4. В Obsidian — «Довериться автору и включить плагины». Справа появится панель «Второй мозг».
5. Настройки → Второй мозг → «Модели»: ключ API, модель профиля, «Проверить связь» (раздел 13).
6. Заметки — в `_staging/архив/`, затем «Запустить Фазу 1» в мастере первой загрузки (раздел 18.2).

Если `Установка.bat` запущен прямо из архива (из временной папки Windows), он просит сначала распаковать архив.

**Повторный запуск** `Установка.bat` чинит установку: заново ставит библиотеки и плагин, пересоздаёт сломанное окружение. Настройки, ключи и заметки он не трогает. Его стоит запустить, если папку программы перенесли, Python переустановили или плагин пропал из хранилища.

### 19.3 Обновление

**Откуда.** Источник новых версий — репозиторий GitHub, ссылка на который вписана в саму программу: строка `UPDATE_REPO` в `brain/__init__.py` (вида `https://github.com/имя/репозиторий`). В настройках пользователя её нет. Пустая строка — обновления не проверяются, кнопка «Проверить обновления» неактивна. Репозиторий должен быть открытым.

Новая версия берётся из последнего релиза репозитория: архив программы среди файлов релиза (`.zip` с «мозг» или «brain» в названии, иначе первый `.zip`), а если его нет — архив исходников релиза. Если релизов нет — ветка по умолчанию; её версия — `__version__` из `brain/__init__.py`. Версии сравниваются по числам: `2.10.0` новее `2.9.1`.

**Что меняется.** Папки `brain/`, `prompts/`, `plugin/`, `plugin-src/`, `tests/` и файлы в корне папки программы (`.bat`, `.md`, `.txt` и образец `settings.template.yaml`). Модули `brain/`, которых нет в новой версии, удаляются; `.bat`-файлы прежних версий — тоже. Если изменился `requirements.txt`, программа доустанавливает библиотеки. Плагин копируется и в хранилище, если он там установлен. Если в новой версии строка `UPDATE_REPO` пустая, а в установленной вписана ссылка, ссылка сохраняется — иначе программа перестала бы видеть следующие версии.

**Не трогается никогда:** `settings.yaml` и `settings.yaml.bak`, файлы ключей и токенов, хранилище. `installed.json` из новой версии не копируется — программа пишет его сама, с контрольными суммами только что установленных файлов.

**Промпты, которые правил пользователь.** `installed.json` хранит контрольные суммы установленных файлов. Если промпт отличается от установленного (его правили), то: в новой версии этот промпт не менялся — остаётся пользовательский; менялся — ставится новый, а пользовательский копируется в `prompts/_прежние/<имя> (<дата> <время>).md`, и итог обновления об этом говорит.

**Как запускается.**

- **Из плагина.** При запуске Obsidian (если включено «Проверять при запуске Obsidian», `updates.check_on_start`) плагин выполняет `update --check`. Если версия новее, окно «Вышла новая версия»: номер, откуда, описание релиза и «Установить», «Позже», «Пропустить эту версию». Пропущенная версия при запуске больше не предлагается, следующая — снова; кнопка «Проверить обновления» в настройках (вкладка «Основное») проверяет сразу и показывает любую новую версию. «Установить» выполняет `update --yes`: обновление встаёт в очередь плагина и начинается после текущего запуска. Затем окно «Перезапустить Obsidian»: новый плагин заработает после перезапуска.
- **Из консоли.** `python -m brain update` спрашивает подтверждение; `--yes` — без вопроса, `--check` — только проверить, `--force` — установить, даже если версия не новее.
- **Вручную.** Новый архив распаковывается поверх папки программы, затем запускается `Установка.bat`: он доставит библиотеки и обновит плагин в хранилище. В архиве нет `settings.yaml` и ключей, поэтому настройки не затираются. Изменённые промпты при ручной распаковке заменяются новыми — копии своих правок нужно сохранить заранее. Если `Установка.bat` не запускать, плагин при следующем запуске Obsidian заметит, что в папке программы лежит плагин новее, и предложит установить его и перезапустить Obsidian.

## 20. Команды программы

Обычно команды запускает плагин. Из консоли — в папке программы, Python-окружением `.venv`:

```
.venv\Scripts\python.exe -m brain <команда> [параметры]
```

Без команды программа печатает их список. В консоли вопросы задаются прямо в окне: номер варианта или «д/н».

**Общие параметры** (пишутся перед командой):

| Параметр | Что делает |
| --- | --- |
| `--settings <путь>` | Другой файл настроек; по умолчанию — `settings.yaml` рядом с программой. |
| `--vault <папка>` | Другое хранилище; `settings.yaml` при этом не меняется. Плагин всегда передаёт открытое хранилище. |
| `--json` | В конце — строка `@@RESULT {…}` с итогом (для плагина, раздел 18.1). |
| `--ask-stdin` | Вопросы посреди запуска — строкой `@@ASK {…}`; ответ — строкой JSON `{"choice": N}` в стандартный ввод (раздел 18.4). |

**Команды:**

| Команда | Что делает |
| --- | --- |
| `run [--yes]` | Фаза 1: принять ответы на вопросы и ручные правки, обработать всё новое из `_staging`, пересобрать базы синтеза (раздел 6). Перед большим запуском — оценка и вопрос; `--yes` — без вопроса. |
| `synth [контейнер] [--force] [--yes]` | Фаза 2: написать или обновить документы контейнера (раздел 8). Без названия — выбор из списка. Если с прошлого синтеза ничего не менялось, модель не вызывается; `--force` — переписать всё равно. |
| `revalidate [контейнер] [--ask] [--yes] [--count]` | Глубокая перепроверка раскладки (раздел 10.1). Без названия — все записи; `--ask` — выбрать контейнер из списка; `--yes` — без подтверждения; `--count` — только посчитать записи. |
| `patterns` | Поиск новых составных типов аспектов (раздел 10.4). |
| `advise [контейнер]` | Совет модели по порогам контейнера; сам ничего не меняет (раздел 10.5). Без названия — выбор из списка всех контейнеров. |
| `answer <QID> --option <N>` или `--text "<ответ>"` | Ответить на вопрос сразу, не дожидаясь Фазы 1. Варианты нумеруются с нуля (раздел 7.3). |
| `check` | Проверить настройки и хранилище, каждую различающуюся модель — основную и моделей шагов — пробным обращением, эмбеддинги — пробным вектором. Итог по каждому пункту отдельно. |
| `status` | Что сейчас в работе: записи, вопросы, очереди, расходы. |
| `usage [--reprice <профиль\|emb\|all>]` | Расходы: за сегодня, месяц, всё время, по профилям и шагам (раздел 14.5). `--reprice` — пересчитать стоимость прошлых обращений по текущим ценам профиля, эмбеддингов или всех (раздел 14.2). |
| `estimate run`, `estimate synth <контейнер>`, `estimate revalidate [контейнер]` | Оценка запуска без запуска: обращения, время, стоимость (раздел 14.4). |
| `llama status [--hw]` | Своя модель эмбеддингов (раздел 12.3): что скачано, запущен ли сервер; `--hw` — ещё и оборудование компьютера. |
| `llama start [--params-json <файл\|->]` | Скачать недостающее и запустить сервер модели; параметры запуска — JSON из файла или стандартного ввода. |
| `llama stop` | Остановить сервер модели. |
| `llama download [--yes]` | Только скачать модель и llama.cpp. `pull-embeddings` — то же самое. |
| `update [--check] [--yes] [--force]` | Обновить программу с GitHub (раздел 19.3): `--check` — только проверить, `--yes` — без вопроса, `--force` — даже если версия не новее. |
| `snapshot` | Переписать снимок `.system/ui.json` для плагина (раздел 18.1). |
| `settings` | Схема и текущие значения настроек в JSON — по ним плагин строит окно настроек. |
| `settings --set-json <файл\|->` | Применить изменения настроек из JSON: проверить, переписать `settings.yaml` с пояснениями, прежний — в `settings.yaml.bak` (раздел 17.2). |
| `settings --key profile:<id>` или `--key embeddings` | Сохранить ключ из стандартного ввода в файл ключа профиля или облачных эмбеддингов. |
| `install-plugin [хранилище]` | Только установить плагин в хранилище (раздел 18.1). |
| `setup [хранилище]` | Установка «всё в одном» — её запускает `Установка.bat` после библиотек (раздел 19.1). |

Контейнер в командах указывается названием — можно без кавычек (`synth Книжный клуб`), частью названия, если она однозначна (`synth Пульс`), или `id` (`synth k004`).

Любая команда, кроме `setup`, заодно убирает из папки программы `.bat`-файлы прежних версий.

**Коды выхода:**

| Код | Значение |
| --- | --- |
| 0 | Готово. |
| 1 | Понятная ошибка (нет ключа, сервер не отвечает, неверное значение настройки) или остановка — в выводе сказано, что сделать. |
| 2 | Непредвиденная ошибка программы. Подробности — в `_логи/ошибки.log`; всё обработанное до неё сохранено, повторный запуск продолжит с того же места (раздел 15.4). |

## 21. Карта кода

### 21.1 Программа (`brain/`)

Программа на Python 3.10+, библиотеки — PyYAML, requests, numpy и dulwich (git без установки git). Точка входа — `python -m brain` (`__main__.py` → `cli.py`).

**Путь данных в Фазе 1:** `cli.py` берёт блокировку хранилища и собирает контекст (`context.py`) → `phase1.py` применяет ответы (`answers.py`) и ручные правки (`vault.py`), принимает файлы (`ingest.py`) → черновик структуры (`structure.py`) или классификация (`classify.py`) → шаги каждой записи (`pipeline.py`: вопросы, уплотнение, векторы через `embed.py` и `index.py`, извлечение аспектов) → сборка баз синтеза (`synthesis_base.py`) → витрины (`views.py`), версии (`versions.py`), вопросы (`questions.py`), снимок для плагина (`snapshot.py`). Все обращения к модели идут через `llm.py` с промптами из `prompts.py`, расход пишет `logs.py`.

| Модуль | Что делает |
| --- | --- |

| `versions.py` | Версии баз синтеза и документов в git-зеркале `.system/versions/` (раздел 11.2). |
| `views.py` | Витрины `_аспекты.md` и `_база синтеза.md`. |
| `snapshot.py` | Снимок `.system/ui.json` для плагина (раздел 18.1). |
| `install.py` | Установка плагина в хранилище, поиск хранилищ Obsidian, уборка файлов прежних версий (раздел 19.1). |
| `updater.py` | Обновление с GitHub (раздел 19.3). |

Промпты — файлы Markdown в `prompts/` (раздел 9). Тексты интерфейса, сообщения программы и промпты — на русском.

### 21.2 Плагин (`plugin-src/`)

Плагин написан на TypeScript; esbuild собирает его в один файл `plugin/main.js`, рядом кладёт `manifest.json` и `styles.css`. Сборка: Node.js 18+, в папке `plugin-src` — `npm install`, затем `npm run build` (сначала проверка типов, потом сборка). После сборки — `install-plugin` или «Установка.bat» и перезапуск Obsidian.

| Файл | Что делает |
| --- | --- |
| `src/main.ts` | Сам плагин: команды палитры, панель, строка состояния, чтение снимка `ui.json`, правки YAML через API Obsidian, уведомления Windows, проверки при запуске Obsidian (плагин новее в папке программы, новая версия на GitHub), установка обновления и перезапуск. |
| `src/engine.ts` | Запуск программы, очередь запусков, «Стоп» и «Прервать сразу», разбор живых строк и итога `@@RESULT`, ответы на `@@ASK`. |
| `src/view.ts` | Панель: блок текущего запуска и вкладки «Обзор», «Вопросы», «Контейнер», «Расходы», «Журнал». |
| `src/settings.ts` | Окно настроек по схеме программы: вкладки, поиск, профили, модели шагов, ↺, автосохранение, блок «Своя модель». |
| `src/modals.ts` | Окна: подтверждение, выбор варианта, текст, выбор контейнера, «Новая мысль», совет по порогам, проверка связи, параметры своей модели. |
| `src/report.ts` | Ошибки плагина: перехват, красная рамка, `плагин.log`, «Отчёт для разработчика». |
| `src/types.ts`, `src/util.ts` | Типы снимка и вспомогательные функции. |
| `styles.css` | Оформление на переменных темы Obsidian: светлая и тёмная темы, узкая колонка. |
| `manifest.json`, `package.json`, `tsconfig.json`, `esbuild.config.mjs` | Описание плагина, зависимости сборки, настройки TypeScript и сборки. |
| `tests/` | Проверки плагина (раздел 22.2). |

**Имена в классах.** Классы плагина наследуют классы Obsidian (`Plugin`, `PluginSettingTab`, `ItemView`, `Modal`, `FuzzySuggestModal`). Свои поля и методы нельзя называть так же, как внутренние члены этих классов: Obsidian вызывает их сам, и одноимённый член плагина ломает, например, окно настроек. Можно — только открытое API из `obsidian.d.ts` и методы, которые Obsidian ждёт от плагина (`onload`, `display`, `onOpen`…). Это проверяет тест в настоящем Obsidian (раздел 22.2).

## 22. Проверки

Программу и плагин можно проверить целиком без настоящей модели, без интернета и без Windows: вместо модели отвечает тестовая, вместо GitHub, Hugging Face и провайдера — локальные имитации.

### 22.1 Программа (`tests/`)

**Тестовая модель.** `tests/fake_llm.py` даёт правдоподобные ответы по простым правилам на все промпты (раздел 9.2) и один раз нарочно отвечает с ошибкой формата — чтобы проверить исправление ответа. Включается в настройках: `llm.mode: fake` (модуль — `llm.fake_module`, по умолчанию `tests/fake_llm.py`) и `embeddings.mode: fake` — тестовые векторы вместо модели эмбеддингов.

| Проверка | Что проверяет | Запуск |
| --- | --- | --- |
| `smoke.py` | Сквозная проверка с тестовой моделью, от пустого хранилища (см. ниже). | `python tests/smoke.py [папка]` — по умолчанию во временной папке |
| `api_mock.py` | Сетевой слой без настоящего провайдера: локальный сервер в формате OpenAI (`chat/completions` и `embeddings`) с ошибками 429, 500 и 401, оборванным ответом и ответом не в JSON; профили моделей и их ключи, токены из ответа провайдера и из счётчиков llama.cpp, кэш, стоимость, бюджет и лимит профиля, пересчёт по новым ценам, облачные эмбеддинги с ценой. | `PYTHONPATH=. python tests/api_mock.py` |
| `big_file.py` | Большой файл: деление на порции под окно модели и продолжение после сбоя посередине без дублей. | `python tests/big_file.py [папка]` |
| `update_mock.py` | Обновление без интернета: локальный сервер в формате GitHub API — последний релиз с архивом программы, архив исходников, репозиторий без релизов (ветка, дерево файлов, архив ветки), ошибки. Настройки и ключи не тронуты, изменённые промпты — в `prompts/_прежние`, устаревшие модули и `.bat` прежних версий убраны, плагин в хранилище обновлён. | `python tests/update_mock.py` |
| `fake_llama.py` | Не проверка, а имитации для своей модели эмбеддингов: Hugging Face (список файлов и файл модели с докачкой), релизы llama.cpp на GitHub и ненастоящий `llama-server` на Python (`--help`, `--list-devices`, `/health`, `/v1/models`, `/v1/embeddings`). Ими пользуются `smoke.py` и тест плагина. | — |

**Что проходит `smoke.py`:**

1. Массовая загрузка архива: даты, подсказки, диалог с ИИ, файл в cp1251, пустой файл, картинка.
2. Правка и утверждение черновика структуры.
3. Раскладка, вопросы, аспекты, базы синтеза.
4. Ответы на вопросы и правки YAML, в том числе перенос записи (оспорить раскладку).
5. Новая мысль, которая пересматривает старую, — устаревание аспекта.
6. Фаза 2: документы и версии.
7. Ручная правка документа → новая запись → пересборка.
8. Правка текста обработанной записи, забытый росток, сбой посреди прогона и продолжение.
9. Смена модели эмбеддингов — пересчёт векторов.
10. Ручной режим через веб-чат.
11. Повторный прогон без нового — без обращений к модели.
12. Прочие команды.
13. Ручные правки: тип по-русски, контейнеры, заведённые вручную.
14. Команды для плагина: снимок, ответы, настройки, свои пороги контейнера, совет по порогам, «Стоп», установка плагина.
15. Перенос настроек прежнего вида, дневник по датам, оценка запуска, вопросы через стандартный ввод (запустить, отмена, закрытое окно), живые строки хода работы, журнал расходов и сводка.
16. Установка «всё в одном»: поиск и выбор хранилища, `setup` целиком, уборка `.bat` прежних версий.
17. Своя модель эмбеддингов: скачивание с имитаций, запуск, автозапуск, остановка, неверные параметры; обновление, когда ссылка на репозиторий не вписана.

### 22.2 Плагин (`plugin-src/tests/`)

**Тест на имитации Obsidian** — `run_e2e.py`. Собранный плагин запускается в Chromium на имитации API Obsidian (`obsidian-mock.js`, `harness.html`: рабочая область, хранилище, YAML, окна, настройки, запуск процессов) вместе с настоящей программой и тестовой моделью и проходит весь путь пользователя: мастер первой загрузки, ожидание ответа модели, утверждение структуры, вопросы, пороги (ползунок, ↺) и совет по порогам, стиль, Фаза 2, «Новая мысль», настройки (вкладки, поиск, профили, модели шагов), ход запуска «N из M», «Стоп», «Расходы» (цены, пересчёт, бюджет), вопросы о бюджете и большом запуске, уведомления, журнал, тёмная тема, установка плагина из папки программы, обновление с имитации GitHub, своя модель эмбеддингов (окно параметров, скачивание с имитаций, запуск ненастоящего `llama-server`, адрес в настройках, «Остановить»). Снимки экрана — в `<папка>/shots`.

```
pip install pyyaml requests numpy dulwich playwright
playwright install chromium
python plugin-src/tests/run_e2e.py /tmp/e2e
```

**Тест в настоящем Obsidian** — `run_real.py`. Имитация знает об Obsidian только то, что в неё вписали, поэтому тот же плагин проверяется и в настоящем Obsidian для Linux (распакованный архив с github.com/obsidianmd/obsidian-releases) на виртуальном экране Xvfb; управление — через протокол отладки Chromium. Путь: установка командой `setup`, «Довериться автору и включить плагины», мастер, Фаза 1 и утверждение структуры, вкладки панели, настройки в отдельном окне и модальным окном (все вкладки, поиск, пороги, профиль с подтверждением удаления, проверка связи), «Новая мысль», выбор контейнера, ошибка в плагине (рамка, буфер обмена, `плагин.log`), отчёт для разработчика, ошибки консоли во всех окнах.

Последний шаг сверяет имена в классах (раздел 21.2): имена полей и методов каждого класса плагина сравниваются с именами работающего Obsidian — цепочкой прототипов базового класса и полями его пустого экземпляра, за вычетом открытого API и методов, которые Obsidian ждёт от плагина. Совпадение — ошибка теста. Имена Obsidian сохраняются в `obsidian-names.json` — с ними удобно сравнить следующую версию Obsidian.

```
python plugin-src/tests/run_real.py /путь/к/obsidian-<версия> /tmp/real
```

`run_e2e.py` рассчитан на Linux или macOS (он готовит тестовую копию программы с `.venv/bin/python`), `run_real.py` — на Linux с Xvfb; `REAL_KEEP=1` — не закрывать Obsidian после теста.
